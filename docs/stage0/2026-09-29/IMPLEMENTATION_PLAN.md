## 4. 资金事实、履约状态与席位：拟定设计基准

以下为待 D0 批准的推荐政策。资金事实独立记录，不用 Order.status 充当账本。记录真实渠道、商户作用域、原交易关联、金额/币种及验证来源；额外成功交易必须可独立保存，不因订单唯一约束而被拒绝记录。

| 事件/前提 | 必须保存的资金事实 | 订单/履约处理 | 席位与补偿 |
| --- | --- | --- | --- |
| 待付订单正常收款 | 该渠道流水成功；回调与查单共用业务幂等 | 进入有明确成团截止时间的待成团 | 保有容量；此时无需立即有最终桌位 |
| 同笔成功经不同 nonce/事件/查询确认 | 同一资金事实，多来源可追溯 | 不重复推进 | 不重复占位、通知或退款 |
| 本地 CLOSED 后确认成功 | 仍记录真实成功，原订单保留关闭事实 | 首发建议不自动重开；进入异常退款处置 | 不抢占已释放席位；绑定这笔收款生成退款义务 |
| 同订单第二笔不同成功流水 | 两笔成功分别保留 | 原正常履约不重复执行 | 额外收款进入逐笔退款/异常认领 |
| 支付或退款超时、网络断开 | 结果未知与外发标识仍存在 | 不据此认定资金失败 | 查单恢复；超过时限升级，不无限静默挂起 |
| 退款成功先于原请求报错 | 保留成功退款事实 | 后到失败分支不得覆盖 | 不重新创建另一笔退款 |
| 成团失败/运营取消 | 对成功收款建立一次退款义务 | 停止该次履约，展示退款进度 | 释放规则由事务统一执行，义务不中断 |
| 草案成员变化 | 资金事实不变 | 旧草案失效；按当前有效成员重建 | 不能强行确认失效成员 |
| 草案后晚到付款 | 保留资金成功事实 | 决策前可重建纳入；决策后默认退款处置 | 不隐式给未入桌用户解锁地址 |
| 实际履约已完成 | 保留成功收款及履约记录 | COMPLETED 不被旧支付请求回退 | 后续例外按单独获批政策审计处理 |

对长时间未知结果：配置自动查询预算、成团决策最晚时刻、人工接管时限与负责人。进入活动决策截止仍无法确定时，活动不得假装满足成团条件；进入受控延期或取消处置并告知用户，政策由产品批准。后续确认成功仍必须认领与补偿。

### 4.1 退款审核拒绝状态表

拒绝的只是该次用户申请，不能抹去由活动取消等产生的独立退款义务。判断在同一事务内读取当前活动、资金、席位与申请版本：

| 当前事实 | 拒绝后的合法处理 |
| --- | --- |
| 未成团、仍在有效报名/决策期、实收有效 | 可恢复待成团，保留原容量；记录拒绝原因 |
| 活动已成团、原桌位仍有效 | 可恢复 GROUPED；不可凭历史状态恢复不存在的桌位 |
| 活动已取消/失败 | 不恢复履约；保留或生成系统退款义务 |
| 桌位已失效/发生重排 | 重新判断合法分配；不能分配则异常/退款处置 |
| 活动已完成 | 有实际履约证据才可归入 COMPLETED；仅时钟已过不能视为完成 |
| 已有成功退款或不可撤销的渠道退款处理中 | 旧审核拒绝不能覆盖资金结果；返回当前结果或冲突并审计 |

用户 T-24 前后均按已获批政策进入不同审核口径；活动开始后的默认不允许路径与人工例外必须分别实现，不能以页面文字代替 API 约束。

### 4.2 三类约束必须分别维护

以下是推荐初始分类，D0 要把每个现有/新增状态落到数据库谓词与测试。状态之外的资金未知、退款义务和席位占用以持久字段/关联记录表达，不靠当前时间索引隐式变化。

| 情况 | 阻止同活动重报 | 保留容量/席位 | 尚有资金处理责任 |
| --- | --- | --- | --- |
| PENDING_PAYMENT；包括到期但渠道结果未知 | 是 | 是，直到可靠关单/决策完成 | 有外发意图或未知结果时是 |
| PAID_PENDING_GROUP / GROUPED | 是 | 是 | 正常实收已确定；仍有未来履约责任 |
| REFUND_REQUESTED / REFUND_REVIEWING / REFUNDING | 是 | 初期保守保持现有占位，释放另由获批事件触发 | 是 |
| GROUP_FAILED | 是；活动也已禁止报名 | 不再分配履约席位 | 成功实收未退清则是 |
| COMPLETED | 是 | 保留历史实际席位，不重新销售 | 正常结清为否，异常另记 |
| CLOSED / CANCELED / PAYMENT_FAILED | 可靠确认未收款且无未决意图时否 | 确认退出后释放 | 若后续查到资金/未知结果则是 |
| REFUNDED | 活动仍可报名且无其他未决事项时否 | 释放，保留历史桌位记录 | 全部关联退款结清时否 |

订单“可重报”与“资金已清”不由一个 enum 单独决定。活动已截止/取消/完成时，即使历史订单不再阻止重报，活动门禁仍拒绝新订单。最终索引候选为持久 `registrationActive` 标记的部分唯一约束，或独立有效报名占位表；推荐优先评审前者，具体方案、迁移 SQL 和维护它的全部写路径在 D0 冻结。禁止仅删除现有唯一索引，禁止以 `now()` 作为索引谓词。

## 5. 阶段 2 必须运行的机制

### 5.1 幂等与事务

- 资金事实键：渠道 + 商户作用域 + 渠道交易/退款标识；原支付和退款必须明确关联。
- 通知接收键：渠道 + 商户 + 通知事件 ID，另存内容摘要。相同 ID 不同内容形成冲突证据，不能覆盖原事件。
- 业务意图键：订单/原收款 + 操作类型 + 持久意图 ID。同一未结清意图重试沿用原商户号；确定关闭后才按规则创建新尝试。
- 退款额度以原成功收款为单位，在锁内计算已成功及处理中额度；未知退款继续占用预算。
- 涉及活动和订单的路径统一按活动 → 排序后的订单 → 资金意图/桌位的顺序加锁，重读关联与版本；认领未知关联事件前不假造订单。
- 状态条件更新核对影响行数；资金事实、业务变化、审计、后续义务/初始任务在事务中一致提交。网络请求不在持锁事务内。
- 大活动可分批处理，但必须有持久批次/逐单游标、唯一义务键和待补扫记录，不允许“标记全退完成”后才开始无记录循环。

### 5.2 持久任务最小运行器

拟新增任务字段：业务唯一键、类型、关联 ID、状态、可运行时刻、尝试次数、租约到期、领取者、执行代次、脱敏错误分类、人工责任人/截止时间。载荷不存 Secret 或无必要的个人信息。

执行协议：

1. 短事务领取到期任务，使用 `FOR UPDATE SKIP LOCKED`，增加执行代次并记录租约；该机制只用于任务领取。
2. 提交领取事务后，在事务外请求渠道；超时受控，使用原商户业务标识。
3. 任务完成/重试提交必须匹配领取者、执行代次和合法业务前态。旧代次不能改变新任务状态。
4. 租约过期可由另一 worker 接管。A 过期后返回的可信渠道证据可交统一幂等入口复核，但 A 不能强写旧状态；B 已成功时不回退。
5. 采用至少一次执行语义，不宣称外部 HTTP 恰好一次。无法确定是否受理时先查询，不生成新号“重试”。
6. 按错误分类有限重试、退避；预算耗尽转人工待办，记录负责人、截止时间、告警与复核。任务和资金意图不删除。

阶段 2 交付独立 worker 编译产物和运行命令，两个独立进程实际测试租约、崩溃和接管。阶段 3/5 复用同一机制，不能先靠临时定时器宣称恢复完成。

### 5.3 回调可靠接收协议

推荐首发流程：原始字节 → 入口限长/格式/时效与可信材料验签 → 解密及规范化 → 短事务保存最小可信事件与处理任务 → 确认提交 → 按批准的渠道协议应答 → 异步应用业务结果。

- 最小事件包含恢复所需的交易标识、金额/币种、商户关联、入口接收时间、验签材料 ID、事件摘要及验证结果；敏感内容受控存储，不进入普通日志。
- 若格式/解密无法完成但已验签可信，保存受控隔离证据及待办；是否应答按商户协议冻结。不得静默丢弃。
- 保存失败返回失败，不先应答成功；已可靠接收的重复事件在确认持久记录后可成功应答。
- 可信但关联不到本地交易的事件可靠隔离，进入认领/对账待办；不能只无限要求渠道重发。
- 无效签名不成为可信事件；事件冲突另存证据并告警，不覆盖合法记录。
- 处理积压以入口接收时的验签记录为准，不将任务消费时间当作新网络请求时间。
- 回调事件去重和资金业务效果去重分开；查询发现的同笔成功使用同一个资金事实入口。
- 目标应答时延设为低于渠道超时窗口并留余量；以实际代理链路和数据库延迟测试证明。渠道的具体成功应答和超时规则在 X1 前按已确认商户模式核对，不能仅凭报告引用放行。

AT03、AT09 必须走实际 HTTP/反向代理，覆盖应答后杀进程、落盘失败、原始字节、积压消费；只用 app.inject 不足以验收入口行为。

## 6. 迁移与最低兼容回退版本

当前 `bc25f5b` 依赖 `(userId, activityId)` 绝对唯一。出现多条历史订单后，不把它列为可回退版本。

推荐版本顺序：

| 数据库/程序组合 | 允许范围 | 放行条件 |
| --- | --- | --- |
| DB0 + 基线 B | 现状复测，隔离模式 | 不代表可生产发布 |
| DB1 新增结构、保留旧唯一 + 新兼容 C | 重报关闭；验证新事实/任务读取 | 兼容 C 支持多历史查询与新事件协议；旧写入进程必须排空 |
| DB2 新约束生效、旧唯一退出 + C/新版本 N | 可在批准开关下重报 | 预检查、回填、约束存在性及并发测试通过 |
| DB2 + 基线 B | 禁止 | 基线对多历史订单的假设已失效 |
| DB2 + 指定 C 回退 | 拟允许 | C 的具体 SHA、产物摘要和演练结果登记后才允许 |
| 新旧 worker 同时运行 | 默认禁止跨协议代际混跑 | 仅在同任务/事件版本兼容、领取隔离及幂等测试通过后允许 |
| 旧/新客户端 + C/N API | 按兼容表允许或明确拒绝升级 | 真机验证；旧客户端不能保留模拟成功或越权语义 |

实施步骤：新增兼容结构/约束 → 兼容应用就绪但关闭重报 → 停止旧写入者并验证 → 数据预检查/回填 → 批准窗口退出旧唯一约束 → 打开重报 → 观察后清理。

D0 提交真实 SQL 草案、约束谓词、重复样本及验证查询；不把 Prisma 对部分索引的支持情况当作既定事实，应按锁定版本核实。历史冲突通过受控判定处理，禁止删除资金历史“过迁移”。

最低兼容回退 SHA：**待 C 实现并验证后填写，目前不存在可声明通过的版本**。这是 G3 阻塞条件，不阻塞 D0 的实验设计。G3 前必须实际运行多历史订单、未知支付、退款中、旧事件、多个 worker 接管及回退场景。

数据库不以破坏性降级作为常规回退；优先关闭新业务、切兼容应用或前向修复。备份恢复是独立事故流程，不能恢复完即重开收费。

## 7. 双向对账与恢复流程

M3 交付最小对账能力及模拟账单测试，X1 验证真实商户账单覆盖，G4 每日执行。白名单允许受控导入加人工复核，无需建设完整财务平台。

### 对账范围

1. 本地意图 → 渠道查询：未知、超时、处理中及本地成功与渠道不一致。
2. 渠道账单 → 本地资金事实：渠道有本地无、额外收款、退款缺失、金额/币种/商户关联冲突。
3. 保存商户作用域、账期、文件摘要校验、导入批次、覆盖状态及重复导入键；未生成/下载失败/覆盖不全均不得记为零差异。
4. 区分交易金额、用户实付、优惠、手续费与结算净额；退款以渠道适用规则和原交易关联核算，不能简单拿净结算金额作退款上限。
5. 每项差异具备发现时间、关联证据、责任人、截止时间、处置方式、复核者和关闭结论。导入不直接任意改订单状态，通过统一资金/补偿服务处理。

### 备份恢复顺序

暂停新收费和不受控自动外发 → 恢复库到隔离验证环境 → 安全接收并持久保存存量可信回调 → 核对恢复点之后及此前未结清交易 → 用渠道账单/查询重建缺失关联和义务 → 检查旧任务避免重复外发 → 兼容程序验收与资金责任人签收 → 恢复受控处理 → 另行恢复新收费。

不能只重放恢复后的本地任务，因为恢复点之后的资金记录和任务可能同时缺失。AT07–AT08 必须证明渠道独有流水、重复文件、不可用账单和恢复点后退款均可发现。
