1. **S3冻结输入中的15项决定。**仅覆盖DR01-01—09、DR02-01—06明确涉及的规则；输入文件状态不是政策生效、技术实施或RV通过证据。

## 2. 产品范围、角色与职责

### 2.1 产品定位与首发范围

**BAS-01｜产品定位。**饭局延续“上海本地餐厅兴趣体验工具”的定位，以活动组织、报名、餐厅安排、排桌、到场履约和售后处理为主。不因内部参考性别而改成同桌性别承诺或关系匹配产品。[S1，第 18—24 行；Q39—Q40]

**BAS-02｜地域。**首发运营上海；允许未来逐步扩展其他城市。允许扩城不等于首发必须实现完整多城市组织、清结算或运营体系。[Q36]

**BAS-03｜用户资格。**仅接受年满 18 周岁的成年人。没有确定年龄核验具体产品方式；不以此自动新增身份证、出生日期或强实名认证。[Q35、Q41]

### 2.2 各角色的业务权限

| 角色 | 主要职责/权限 | 已确认的限制 |
| :--- | :--- | :--- |
| 平台运营主体 | 提供组织服务；处理报名、费用说明、退款、履约争议与补偿安排 | 本文未核实商户号、收款账户、发票与资金结算资质 |
| 用户 | 浏览、报名/候补、付款、取消、扫码签到、申诉/复核、申请注销 | 必须满足准入；不得因收到候补付款凭证就视为已获得桌位 |
| 餐厅 | 确认逐场桌型、容量、费用、接待条件；提供签到二维码；当晚确认正常履约/履约异常 | 无权自行从用户保证金中扣款；运营也不能代餐厅擅改容量参数 |
| 平台运营/客服 | 联系餐厅、通知用户、核实争议、按规则审核、决定获授权的补偿方案 | 不能因客服晚回复改变取消受理时间；不能借人工审核任意改写既定金额规则 |
| 首次审核人员 | 审查履约争议或特殊退款申请 | 普通规则与例外要分别记录；餐厅标签不是已经完成的资金结论 |
| 最终复核人员 | 处理用户一次最终复核申请 | 必须不同于首次审核人员；平台内部最终结论须再次通知 |
| 技术/QA | 将批准规则实现为可验证功能和异常处理 | 不替业务负责人决定待定金额、时限、例外或合规结论 |
| 法务/隐私/资金主责 | 对重要条款、敏感材料、保证金性质、餐厅补偿和结算方式做专项确认 | 本文不冒用这些角色的签收 |

### 2.3 当前明确不扩展的范围

不设用户同桌性别期待，不采集职业/行业、兴趣等复杂画像；首发不提供特殊饮食保障，不代收餐费，不把平台余额或优惠券作为应退款项的默认替代方式。电话和企业微信是后续目标而非已经可用能力。[Q15、Q19、Q39—Q50、Q95、Q100]

**餐厅履约操作必须能真实完成，但操作载体未定。**“由餐厅确认”不等于本轮已批准完整商户后台、独立商户 App 或自动分账产品。[Q08—Q10、Q79—Q80；S1，第 72—82 行]

### 3.3 时间偏好

**USR-06｜用途。**仅用于优先展示符合时间偏好的活动，以及让运营了解开局需求；不作为报名、付款或排桌硬门槛。[Q47]

**USR-07｜选填。**未填写仍可浏览、报名、付款和成团。用户主动报名与偏好不一致的时间，视为主动选择该具体活动，不因长期偏好而拒绝报名。[Q47—Q48]

时间选项清单、是否多选、更新频率和统计展示方式没有被逐项确定，属于产品/技术方案，不由本文补造。

### 3.4 内部性别均衡

**USR-08｜软目标。**尽量男女相对均衡，但不要求 1:1；不能因此阻止本已符合硬条件的桌子成团。[Q40]

**USR-09｜不得覆盖其他条件。**餐厅人数/容量、报名有效性和付费候补 FIFO 优先；不得为了性别均衡跳过候补队首。[Q40、Q59]

**USR-10｜对外表达。**不提供同桌性别期待，不承诺具体男女比例。此项只是经营与产品选择，不能据此写成排除任何用户法定救济的总括条款。[Q39—Q40；S1，第 46 行]

## 4. 费用组成与保证金资金去向

### 4.1 三类金额严格区分

本文统一使用符号：

- `F`：本订单活动服务费。
- `D`：本订单履约保证金。
- `M`：用户到店直接支付给餐厅的餐费及已披露的餐厅收费。

**FEE-01｜平台收费组成。**用户一次合并支付F+D，后台分项记录F与D；付款前展示实际F、D及合计，不能把总额统一当服务费或笼统称票价。支持仅退D、保F退D、F+D全退、D餐厅补偿及PLATFORM_RETAINED。D已退后再批准两项全退仅补剩余F。[Q02；DR01-01]

**FEE-02｜餐费边界。**M 由用户直接向餐厅支付；平台不代收餐费，不参与餐费分账。这不排除本轮新确认的“违约保证金补偿餐厅”。两者不是同一结算事项。[Q15、Q11—Q12]

**FEE-03｜默认价与活动覆盖。**F采用平台默认价+活动级覆盖，活动覆盖优先；默认具体金额仍TBD，不采用历史示例金额。付款前展示实际F、D、F+D；支付/报名生效时保存价格快照，之后F变更不追溯已完成报名订单。[Q13；DR01-05]

**FEE-04｜保证金审核及上下限。**餐厅针对具体活动提出D，平台运营审核批准后形成有效D版本才允许收费；餐厅不能直接改用户收费，平台不能伪造餐厅确认，变更新版本不追溯已付款订单。正常D必须满足D_MIN≤D≤D_MAX；普通活动配置不能放行超界，特殊审批未来另批。D_MIN=TBD、D_MAX=TBD，正式配置与有权签收前不允许真实保证金收费。真实收费还须具备有效餐厅提议/确认和平台审核记录。[Q14；DR01-06/07/08]

### 4.2 付款与退款的金额语义

| 业务说法 | 本文的金额含义 |
| :--- | :--- |
| 服务费全退 | 退还该订单尚未退还的 F 对应金额 |
| 保证金全退 | 退还该订单尚未退还的 D 对应金额 |
| 两项全退 / 全额退款 | 针对 F + D，不自动包含到店直接支付的餐费 M |
| 服务费不退、保证金全退 | 保留 F，退还 D；不是任意比例折扣退款 |
| 保证金不退 | 依具体场景确定平台或餐厅归属；尚处申诉/复核的不等于已经结算 |
| 额外补偿 | 应退款项之外另行决定的补偿，不能替代应退现金 |

同一笔金额不能因为重复申请、重复任务或重复通知被重复退还；发生多笔真实额外收款时，又不能只认一笔而丢弃其他资金事实。[S1，第 108—115、131—135 行]

## 5. 餐厅供给、费用披露与容量

### 5.1 报名前必须确认的餐厅信息

**VEN-01｜真实供给。**餐厅应针对具体活动确认预约时间、桌型、容量、可接待条件、费用、联系人与异常处置。空白模板不构成真实签收。[S1，第 72—100 行]

**VEN-02｜预计消费。**报名付款前必须展示由餐厅确认的预计人均消费区间；仅为参考，不是最终收费上限。实际餐费依现场点单和结算，由用户直接支付餐厅。[Q15—Q17]

**VEN-03｜额外收费。**最低消费、包间费、服务费、茶位费等可预先确定的固定收费必须在付款前展示；不能到店后未经告知直接增加。[Q18]

Q94 允许经用户明确同意变更核心条件，因此“未披露固定费用不得临时增加”不是“任何新费用永远禁止讨论”；正确边界是**不得单方新增或以沉默视为接受**。不同意的用户按变更规则无责退出。[Q94]

### 5.2 正常桌型参数

**用词区分：单桌人数是一桌坐几位参与者；桌数是一场最多开几桌。**两者不可在用户问卷、餐厅确认和容量计算中混用。

**VEN-04｜逐场由餐厅确认四项容量：**

| 参数 | 业务含义 | 约束 |
| :--- | :--- | :--- |
| 最低成团人数 | 一桌达到此人数才具备正常成团资格 | 正常配置在 4—8 人内 |
| 目标人数 | 餐厅优先希望组织的人数 | 只是目标，不是必须达到的门槛 |
| 单桌最大人数 | 该桌可容纳的业务人数上限 | 正常配置在 4—8 人内，不得突破 |
| 本场最大桌数 | 本次活动最多提供多少桌 | 由餐厅确认，不默认无限多桌 |

正常参数必须满足：`4 ≤ 最低人数 ≤ 目标人数 ≤ 最大人数 ≤ 8`。[Q54—Q55]

**VEN-05｜修改权限。**运营无权为方便排桌自行修改这些参数。需要修改时，先重新取得餐厅确认并留存新记录；涉及已售核心条件，还需按第 14 节处理。[Q53—Q54、Q94]

**VEN-06｜多桌标准策略。**平台提供有限、可审计的标准策略集合，餐厅逐场选择并形成供给revision；不全局固定先填满或先铺最低人数。收费前有效确认，运营无新确认不得改变；满足min/target/max/maxTables，性别软目标不突破FIFO、有效顺序或餐厅规则，已成团事实不能仅为优化任意拆除。具体策略枚举为技术设计，不据此代签餐厅或判实现已完成。[Q56；DR02-05；OP-06 CLOSED]

### 5.3 总容量与正式/候补区分

对参数相同的桌型，`单桌最大人数 × 最大桌数` 是一个理论正式席位上限。例如“最大 6 人、最多 3 桌”，上限为 18 人；还应与餐厅实际签收席位一致。[Q55]

候补是独立的等待资格，不得计算成已提供的正式席位。允许付费候补不等于餐厅容量被扩大，也不表示任何一桌可以超过最大人数。[Q57—Q62]

候补每场WAITLIST_MAX机制已定，统一默认数字和资金暴露上限仍待定；异构桌型、餐厅包场押金及额外成本未获确认，见第17节。[DR02-06；OP-08]

### 5.4 低于最低人数的后期例外

**正常成团按餐厅最低人数；T-8h 后另有明确例外。**若因成员退出低于最低人数，餐厅可决定仍按当前人数接待；这时可能出现不足 4 人，不能再对外笼统承诺“所有实际饭局始终至少 4 人”。该例外的通知和用户退出后果见第 7、10 节；其适用下限和条款披露仍待审。[Q72—Q75]

### 5.5 特殊饮食

**VEN-07｜首发不提供特殊饮食保障。**明确需要餐厅专门保障、但本场不提供保障的安排，应在报名/付款前阻止收费；不能等收款后排桌失败，也不能靠用户勾选自行承担风险绕过。[Q19]

**VEN-08｜普通口味不采集。**Q44 已撤掉普通口味偏好，不继续要求填写旧口味问卷。[Q44]

收费前如何以最少信息完成服务适配判断，没有被具体确定；不据此恢复完整饮食、健康或宗教资料采集。特殊申诉的必要证明属于另一情境，不能混入报名问卷。[Q19、Q33、Q44]

| 到达 T-8h 及以后 | 关闭所有新报名；退出后也不招新补位 | 不启用候补 | 维持履约；人数跌破最低值时进入餐厅最终确认 |

来源：Q22、Q58、Q68—Q72。

“到 T-8h 关闭”表示不能把该时刻当作任意延长报名的理由。已经发起但未完成的付款、渠道晚到成功、与截止任务并发的报名如何收口，需在事件边界方案中明确，见 OP-05；本文不把这些订单假定为支付失败。

### 6.3 T-24h 不再是地址解锁时间

T-24h 保留两个主要职责：**最终成团检查、付费候补结束**。地址在正式成团时立即解锁，即使早于 T-24h。[Q25 覆盖旧设计]

### 6.4 时间边界不得混用

Q28 已明确：**普通成团后取消，恰好提前 24 小时的保证金补偿餐厅**，即 `Δ ≤24h` 归餐厅、`Δ >24h` 归平台。

DR02-03现已独立冻结取消等号：普通未成团Δ≥24h两项全退，8h≤Δ<24h保F退D，0<Δ<8h两项不退；适用晚报名用户Δ≥8h保F退D。Δ取服务端可信acceptedAt，不因处理延迟重算。取消等号不解决恰好T-24h新加入分类、未满10分钟但截止后支付成功或失效桌新客类别，继续OP-05。[DR02-03]

## 7. 自动成团、补位与人数下降

### 7.1 成团以“桌”为单位

**FORM-01｜自动成团。**某一桌的有效正式成员达到餐厅确认的最低人数，立即正式成团，不等运营再次点击、不必凑到目标人数。[Q63]

有效正式成员必须有完整可信F+D成功及合法正式席位，不包括候补、未付、失败、UNKNOWN或已经合法退出者；待付10分钟占位不计min。正式容量已满时仅在候补开放且资格满足时取得付费候补。锁位到期释放不终止UNKNOWN资金查询，随后成功按全退义务处理，不恢复席位。具体技术落实仍待实施。[DR01-02/03/04]

**FORM-02｜继续加人。**成团后仍可补至餐厅最大人数。目标人数不是禁止新增成员的上限；真正硬上限是单桌最大人数及本场最大桌数。[Q64]

**FORM-03｜最低已达即可。**T-24h 时“最低 4、目标 6、最大 6”的桌有 5 人，照常举行；不得仅因为未到目标人数判成团失败。[Q69]

### 7.2 T-24h 前的递补与新报名

**FORM-04｜先候补后新报名。**释放席位时，先依付费候补 FIFO 处理有效候补；队列为空后新报名才可直接拿到空位。[Q59、Q68]

**FORM-05｜自动转正不等于整桌必已成团。**候补转正取得正式席位后，仍看该桌实际有效人数是否达到最低值；若已经达到，则用户进入已成团桌；否则处于待成团。[Q60、Q68]

**FORM-06｜可逆。**成团后成员取消导致该桌人数低于最低值，该桌可以失去成团状态，不能继续沿用“首次成团永久不可逆”。[Q65]

### 7.3 T-24h 前成团失效

**FORM-07｜先补人。**成团失效后不立即取消全部订单，重新待成团并继续接受合法新报名/候补递补。[Q66]

**FORM-08｜恢复。**再次达到最低人数则再次成团，并重新开放详细地址。[Q66—Q67]

**FORM-09｜最终失败。**到 T-24h 仍未达到最低人数，该桌失败，剩余仍愿意参加的用户 F+D 全退。无须按这些用户的主动取消档扣费。[Q66]

**已冻结：**曾成团、取消受理时已失效/重新待成团，按当前实际未成团状态进入第10.2节阶梯；历史成团用于审计，不形成永久扣留。恢复后的取消按当时状态与适用类别处理。[DR02-02；OP-02 CLOSED]

### 7.4 T-24h 至 T-8h

**FORM-10｜中间窗口直接补招。**有效已成团且未满桌可直接报名；T-24h时已有效成团、随后在T-8h前因退出低于min的桌，记录失效而不立即终止，继续合法直接补招至T-8h、达min自动恢复、可补至max，全程不恢复候补。到T-8h仍不足停止报名并进入既有餐厅低人数流程；T-24h已失败桌不能重新开放。[Q70；DR02-01]

**FORM-11｜晚报名用户退款例外。**T-24h至T-8h直接加入有效已成团桌、已确定属于晚报名例外的新用户，主动取消按第10.4节的晚报名时间阶梯，不因加入已成团桌立即失去可退保证金资格；失效桌新加入者的类别仍待OP-05，不能由本条扩展。[Q71；DR02-03]

**主体已闭合：**按DR02-01执行失效、直接补招、恢复或T-8h转餐厅决定，保留FORMED→INVALIDATED→RESTORED历史。OP-07/RV-03低人数细则、失效桌新加入者的取消类别交集仍待OP-05；不自行扩展晚报名例外或补偿金额。[OP-01 CLOSED]

### 7.5 T-8h 后

**FORM-12｜停止补招。**到 T-8h 关闭本场所有新报名，之后不因临时空位重新招募或恢复候补。[Q70、Q72]

**FORM-13｜人数仍达最低。**正常履约，无须等目标人数。[Q69、Q72]

**FORM-14｜低于最低则由餐厅决定。**因成员退出跌破最低值，餐厅决定是否仍按实际人数接待。[Q72]

| 餐厅结论 | 其余愿意参加者的处理 | 来源 |
| :--- | :--- | :--- |
| 不继续开桌 | 该桌取消；F+D 全退，并给予由运营决定的额外补偿 | Q73 |
| 愿意继续开桌 | 平台通知实际人数变化；无须其余用户重新确认，订单继续有效 | Q74 |
| 愿意继续，但某位剩余用户因人数少而退出 | 该用户按自身适用的主动取消规则处理，不自动视为无责退款 | Q75 |
| 未回复/尚未决定 | 截止期限与兜底结果没有确认，不得无限维持等待 | OP-07 |

**FORM-15｜责任分别处理。**Q73 的导致人数下降的主动取消者仍按自身取消规则处理，不能因其后整桌取消自动获得全额退款；其他被动受影响者全退加补偿。这个明确决定来自 T-8h 后场景，不把它无条件扩张到所有其他责任争议。[Q73]

**FORM-16｜例外边界。**餐厅同意低于最低人数接待后，如果又有人退出，是否需要再次确认、最低能否低至 1—2 人、以及与用户原付款告知如何一致，均未确定。保留餐厅可继续接待的业务选择，不虚构最低底线。[OP-07]

### 7.6 成团状态示意（业务含义，不是数据库枚举）

```text
T-24h 前：
待成团 → 有效人数达到餐厅最低值 → 自动成团 → 可补至餐厅最大人数
   ↑                                │
   └──── 成员退出使人数低于最低值 ────┘

到 T-24h：
仍未达到最低人数 → 成团失败 → 剩余有效订单两项全退
有效成团         → 继续履约，允许晚报名至 T-8h

T-8h 后：
人数低于最低值 → 餐厅最终确认
              ├─ 继续：通知人数变化，不要求再确认
              └─ 不继续：被动受影响者两项全退 + 补偿
```

T-24h时有效成团桌随后失效 → 直接补招、不候补 → 达min记RESTORED；T-8h仍不足 → 停新报名、餐厅决定。图中历史与当前状态分离；本版由DR02-01闭合OP-01，T-24h失败桌不可复活。

## 8. 付费候补

### 8.1 候补资格

**WL-01｜付费候补及上限。**正式容量已满、候补开放且有效候补人数<本场WAITLIST_MAX时，完整可信F+D成功取得候补，不是正式成员。人数≥WAITLIST_MAX时停止新候补且不创建新候补支付。每场上限必须配置，统一默认数字TBD，不推定无限候补；候补付款在途与上限竞争未覆盖交集仍OP-05/08。[Q57；DR01-02、DR02-06]

**WL-02｜付款前明确说明。**候补身份、自动递补、截止时间与未转正退款，应与正式席位报名有清晰区分。付款成功本身不能显示成“已成团/已安排桌位”。[Q57—Q60]

### 8.2 排序与递补

**WL-03｜FIFO。**严格先到先得；运营不能因性别、偏好或餐厅指定跳过仍有效的前序用户。[Q59]

**WL-04｜自动转正。**在 T-24h 前有合法席位，按 FIFO 自动转正，无须再次确认；转正后应通知用户。用户在付费候补时应已知该机制。[Q60]

**WL-05｜排序定义仍须落地。**“进入候补先后”已经明确，但到底按有效支付完成、渠道成功时间、平台确认时间还是候补资格生成时间排序，以及同一时刻的稳定排序键，并没有逐项确定。技术方案须保持先到先得且留证，不能悄悄改成性别优先。[OP-05]

### 8.3 退出与到期

**WL-06｜主动退出全退。**只要仍处候补，用户主动退出一律 F+D 全退，不适用 24h/8h 扣费。该选择覆盖 Q61 的旧回答。[Q62]

**WL-07｜T-24h 到期。**未获得正式席位的候补自动结束，F+D 全退；不继续占用资格等候更晚空位，不将该情况标为用户主动取消。[Q58、Q62]

**WL-08｜不向后续窗口延续。**T-24h 至 T-8h 仅有正式空位的直接报名，不再恢复原队列。[Q70]

**WL-09｜与退款时效区分。**“自动结束并全退”确定的是资格结束和退款义务，不表示微信资金在该瞬间必定到账；实际发起与到账应遵守第 15 节。系统生成退款是否需要一层人工审核，Q58 与 Q99 没有逐项闭合，见 OP-11。

**WL-10｜退出与转正竞争。**服务端有效事务顺序产生唯一结果：退出先合法生效，候补资格终止并形成F+D全退义务，后续转正不得成功；转正先合法生效，取得正式席位并终止候补身份，后续取消按正式报名实际类别/规则处理。不看客户端时间，记录顺序与事件证据；锁/事务/版本为技术设计。[DR02-04；OP-05 PARTIALLY_CLOSED]

### 8.4 退出重入与剩余边界

主动退出后，如仍开放、未达上限且满足其他资格可重新申请，视为全新候补，获新FIFO序号排到队尾，原优先级不得恢复。WAITLIST_MAX默认数字、候补资金暴露上限、重复报名、到期退款后购买晚报名席位以及付款在途竞争尚未覆盖。OP-08为PARTIALLY_CLOSED，不把“机制主体闭合”当全部边界已关闭。[DR02-06]

## 10. 取消、退款与补偿矩阵

### 10.1 判定维度

退款不能仅依据“订单当前是不是已成团”。至少需要以下业务事实：

| 事实 | 为什么需要 |
| :--- | :--- |
| 用户此刻是候补还是正式席位 | 候补主动退出始终两项全退 |
| 是否属于晚报名窗口加入已成团桌 | 该类用户明确例外适用时间阶梯 |
| 取消被系统受理时刻与适用活动开始时刻 | 判断 Δ 与 24h、8h 档位 |
| 可信取消受理时桌当前成团状态及完整历史 | 失效时按当前未成团阶梯；历史不能替代当前，仍用于审计及类别核验 |
| 谁发起取消、原因是什么、用户属于何类受影响方 | 平台/餐厅取消不能冒用用户主动取消扣费 |
| 是否存在特殊申诉、已批准例外、履约争议/最终复核 | 决定是否允许例外退 D 或 F+D、是否暂缓结算 |
| F、D 原金额与已退/已处置部分 | 不能重复退款或把餐费混入平台退款 |

这些是业务证据要求，不指定表名、数据库列名或代码结构。

### 10.2 普通“未成团用户主动取消”

最初用户原话：

> 提前 24 小时取消，服务费全退，保证金全退；24 小时以内、8 小时外取消，服务费不退，保证金全退；临时不来，服务费不退，保证金不退。

随后 Q04 明确不足 8 小时主动取消两项不退；Q26 将这套规则限制在未成团场景，Q71 又对晚报名用户引用它。

| 取消时距开始 Δ | F | D | 不退D去向 | 状态 |
| :--- | :--- | :--- | :--- | :--- |
| Δ≥24h | 全退 | 全退 | 不适用 | 已冻结，恰好24h包含 |
| 8h≤Δ<24h | 不退 | 全退 | 不适用 | 已冻结，恰好8h包含 |
| 0<Δ<8h | 不退 | 不退 | 补偿对应餐厅，后期实际状态/餐厅细则仍按适用规则 | 已冻结阶梯；OP-07/RV-03不因此关闭 |

等号来源DR02-03；金额判定以服务端可信取消acceptedAt为准，不因后台迟处理改档。

**REF-01｜不拿异常任务延迟制造扣费。**T-24h 本应失败或结束的候补/待成团订单，不能仅因后台未及时处理，就被改算作 T-8h 以内的普通取消。属于哪个事实、义务何时形成，应由事件规则说明，不能把运行延迟转成新扣费理由。[Q58、Q62、Q66]

### 10.3 普通正式成团后的主动取消

适用范围：Q26 的成团后用户主动取消，**不包括 Q71 晚报名例外、不包括平台/餐厅原因、不包括已获准的特殊退款**。

| 取消时距开始 Δ | F | D | D 去向 | 来源 |
| :--- | :--- | :--- | :--- | :--- |
| >24h | 不退 | 不退 | PLATFORM_RETAINED，非ACCOUNTING_REVENUE | Q26—Q27；DR01-09 |
| =24h | 不退 | 不退 | 补偿对应餐厅 | Q28 明确选择 B |
| <24h、活动尚未开始 | 不退 | 不退 | 补偿对应餐厅 | Q27—Q28 |

**REF-02｜成团状态而非付款多少小时。**普通早期报名用户在一桌提前成团后，即使距离活动仍超过 24h，主动取消仍两项不退。这是用户明确选择，不能被旧草案“开始前取消都全退”覆盖。[Q26]

**REF-03｜取消时当前状态。**曾成团、受理取消时已失效/重新待成团，适用第10.2未成团阶梯；当前仍有效成团且为普通类别适用第10.3，适用晚报名例外按第10.4。保留历史，不以曾成团永久扣留；失效桌新加入者类别等未覆盖交集仍待OP-05。[DR02-02；OP-02 CLOSED]

### 10.4 晚报名用户主动取消的明确例外

对象：**T-24h 至 T-8h 期间，直接加入有效已成团桌的新报名用户。**

| 该用户取消时 Δ | F | D | D去向 |
| :--- | :--- | :--- | :--- |
| Δ≥8h | 不退 | 全退 | 原路退用户，恰好8h包含 |
| 0<Δ<8h | 不退 | 不退 | 补偿餐厅 |
| 最终No-show/确认违约 | 不退 | 不退 | 餐厅补偿，争议流程仍适用 |

取消等号由DR02-03冻结。晚报名对象仍为直接加入有效已成团桌的用户；失效桌新报名者不据此自动归类。

Q71 明确选择“仍按普通时间阶梯”，因此这类订单不能仅凭“付款时桌已成团”两项全扣。资格按何种报名/付款生效时间切分、T-24h 恰好加入者的准确归类，见 OP-05。[Q70—Q71]

### 10.5 候补与成团失败

| 情况 | F | D | 额外补偿 | 来源 |
| :--- | :--- | :--- | :--- | :--- |
| 尚在候补，用户主动退出 | 全退 | 全退 | 未约定 | Q62 |
| T-24h 候补仍未转正 | 全退 | 全退 | 未约定 | Q58 |
| 普通桌最终未成团 | 全退 | 全退 | 未统一承诺 | Q05 |
| 曾成团后失效，T-24h 仍无法恢复，剩余用户 | 全退 | 全退 | 未统一承诺 | Q66 |

不能把“平台/餐厅取消要补偿”扩成所有普通未成团或候补未转正都必须补偿；用户没有作出这样的统一选择。

### 10.6 平台、餐厅原因及后期低人数

| 情况 | 受影响对象 | F / D | 补偿 | 来源 |
| :--- | :--- | :--- | :--- | :--- |
| 平台或餐厅原因取消，无论是否成团 | 因此无法参加的用户 | 两项全退 | 必须额外补偿，方案由运营决定 | Q06、Q29—Q30 |
| T-8h 后因他人退出跌破最低，餐厅不继续接待 | 剩余愿意参加者 | 两项全退 | 必须额外补偿，运营决定 | Q73 |
| 上一行中导致人数不足的主动取消者 | 原主动取消用户 | 按其本人适用规则 | 不因后续整桌取消自动增加其退款权利 | Q73 |
| T-8h 后餐厅愿以较少人数继续，用户因人数少退出 | 该退出用户 | 按本人主动取消规则 | 不因此自动补偿 | Q74—Q75 |
| 换餐厅，用户拒绝或确认超时未回复 | 不接受替换者 | 两项全退 | 原餐厅承担额外补偿责任；覆盖对象/金额见 OP-09 | Q92—Q93 |
| 其他核心条件变化，用户不接受 | 不接受变更者 | 两项全退 | 是否统一额外补偿未单独明确 | Q94 |

**REF-04｜原因优先。**平台/餐厅原因无法履约，不能因用户操作了“退出/退款”按钮就变成普通用户主动取消。[Q29、Q92—Q94]

**REF-05｜不把补偿变成运营可不给。**运营可以决定补偿形式和程度；对于已明确“需要补偿”的场景，不能把 Q30 解读成“可自行决定完全不补偿”。[Q30]

### 10.7 正常履约、No-show 与特殊申诉

| 情况 | F | D | 备注 |
| :--- | :--- | :--- | :--- |
| 正常履约 | 正常收取，不退 | 全退 | 餐厅当晚确认，平台次日核对发起 |
| No-show/最终确认履约违约 | 不退 | 不退，补偿餐厅 | 具体认定、申诉、复核与结算见第 12 节 |
| 特殊情况申诉获批方案 1 | 不退 | 全退 | 运营决定并留依据 |
| 特殊情况申诉获批方案 2 | 全退 | 全退 | 运营决定并留依据 |
| 特殊情况申诉未获批 | 恢复本人原适用普通规则 | 恢复本人原适用普通规则 | 不因审核耗时重新计算取消发生时间 |

特殊申诉只明确了两种获批方案，**未授权按任意百分比退款、只退服务费不退保证金或额外罚金**。[Q32—Q34]

### 10.8 原路退款与资金结果

**REF-06｜原路优先。**正常保证金退还、主动取消退款、失败退款、例外退款均原则上原支付渠道原路退回。原渠道客观不能完成时才进入人工异常处理；不默认转余额、不用优惠券替代应退现金。[Q100]

**REF-07｜真实收款及超时晚到。**每笔可信实收保留独立事实；待付10分钟到期即释放、UNKNOWN继续查询，随后确认成功建立F+D原路全退义务，不重抢席位、不超售。其他关闭后收款、额外重复款和未知退款仍追踪处置，不因订单关闭抹除。本轮无实现/渠道复验。[S1，第108—115、131—135行；DR01-04]

**REF-08｜不重复使用同一保证金。**处于待退款、申诉/复核或补偿归属尚未确定的 D，不能同时作为可结算餐厅补偿和已确认平台收入。业务账务细分与回退规则属于技术/资金设计，不在本文指定实现。

<a id="sec-11"></a>
## 11. 签到、履约确认与正常退保证金

### 11.1 到店签到

**FUL-01｜用户扫码。**由餐厅提供该场饭局签到二维码，用户使用小程序扫码形成到店记录。[Q09]

**FUL-02｜扫码不是完整履约结果。**用户已扫码并不自动等于正常履约，也不直接触发保证金退款；餐厅仍须确认正常/异常。[Q08—Q10、Q79]

二维码由谁生成、有效时段、是否滚动更新、防远程代签、断网/忘记扫码怎么办，本轮未确定。团队应给出最小可用方案，不擅自新增人脸、身份证或精确位置采集。

### 11.2 餐厅确认

**FUL-03｜判断结果分两类。**餐厅在饭局结束后确认“正常履约”或“履约异常”。“尚未确认”是待办进度，不是第三种违约结论。[Q79]

**FUL-04｜当晚完成。**餐厅须在饭局结束当晚完成确认/异常标记。[Q77]

**FUL-05｜不采用自动迟到扣款。**没有选择固定迟到分钟数或一过开始时刻即违约。实际到场和履约由餐厅确认，争议由平台审核；平台尚需确定可对外解释的行为与证据标准。[Q08、Q10、Q79]

“当晚”的具体时刻、午餐和跨午夜活动如何适用没有明确，不能暗自写成 22:00/23:59 等固定期限。[OP-12]

### 11.3 正常保证金退款

**FUL-06｜次日批量。**正常履约者 D 全额原路退，F 正常收取；平台在饭局结束后的次日统一核对并发起退款。[Q07、Q76]

**FUL-07｜不把发起等同到账。**用户端应区分确认完成、待批量退款、已向渠道发起和实际退款成功；不能在商家点了“正常”时直接显示到账。[Q76、Q100]

### 11.4 餐厅漏确认

**FUL-08｜暂行规则 B。**餐厅当晚未完成确认，次日不自动退款，进入运营异常待办，由平台联系餐厅补确认。[Q78 原话“暂时先 B”]

**FUL-09｜不是用户违约。**漏确认不等于用户未到场或履约失败，不据此直接把保证金划给餐厅。[Q78 的承接解释]

联系几次、最晚多久结案、餐厅失联时怎样决定，尚未给出。因此“次日正常退款”不覆盖所有漏确认场景，公开承诺必须区分，不能让异常保证金无限期无责任人。[OP-12]

### 11.5 正常链路

```text
用户到店扫码
→ 留下到店记录
→ 餐厅结束当晚确认
   ├─ 正常履约：次日平台统一核对 → 发起退 D → 跟踪渠道结果
   ├─ 履约异常：暂缓退 D → 进入平台调查和用户申诉流程
   └─ 未确认：次日进入运营待办 → 联系餐厅补确认
```

<a id="sec-12"></a>
## 12. 履约争议、首次申诉与最终复核

> 本节记录的是本轮最明确也最需要审慎评审的资金规则。特别是“48 小时不回复即默认违约”，不得把业务选择等同于已完成重要条款、送达和举证评审。

### 12.1 餐厅可以先报异常，不能直接决定扣款

**DISP-01｜异常入口。**餐厅可先直接标记异常，不要求当场上传完整证据；平台后续联系餐厅了解原因、事实与必要证明。[Q80]

**DISP-02｜保证金暂缓。**异常标记只使 D 进入待审核/暂缓退还，不等于已扣除、已确认为餐厅收入或已经转账。[Q10、Q79—Q80]

**DISP-03｜平台决定。**餐厅提供事实，平台决定是否违约、是否退 D；餐厅无单方扣款权。[Q10、Q79]

### 12.2 首次申诉

**DISP-04｜须听取用户说明。**在作出履约违约与保证金扣除结论前，平台需通知用户并给予说明/申诉机会。[Q81]

**DISP-05｜48 小时。**从用户收到履约异常通知起，给予 48 小时提交说明/申诉；期间 D 保持待审核，不在期限未结束前直接产生最终扣除结论。[Q82]

通知“收到”的可核验方式、无法送达的处理、恰好期限截止的请求顺序未定；不得把站内消息写入数据库自动当作用户已收到。[OP-13]

### 12.3 用户不回应

**DISP-06｜用户已选择的业务规则。**48 小时内完全不回应，按 Q83 的 C 处理：**默认认定违约、保证金不退**。不能把它改写成用户只放弃申诉、平台仍必须另作实体裁决的 A 选项。[Q83]

**DISP-07｜同时保留冲突提示。**Q80 的承接解释曾写“餐厅不能仅凭异常标签、没有足够事实就没收保证金”；而 Q83 并未明确“默认违约是否仍要求餐厅证据达标”。二者交集尚未闭合。需要审定餐厅举证前提和送达条件后，才能把超时写成自动扣保证金触发器。[OP-13]

默认首次认定违约也仍需进入后续结果通知和最终复核申请窗口，不能因用户第一轮未回复而自动剥夺已经选择的复核机制。[Q85—Q88 的流程关联]

### 12.4 首次审核结果与通知

**DISP-08｜结果。**用户提交材料时，平台综合餐厅、用户、签到和相关记录作出首次结论。最终是否违约由平台决定。[Q79—Q81]

**DISP-09｜通知是后续复核的起点。**用户收到首次处理结果后可申请最终复核，必须有对应结果通知和时间证据。[Q85—Q86]

Q84 的助手建议是通知“处理原因、扣除金额、保证金去向、处理时间”等；用户没有对该题独立回 A，故这些具体展示字段保留为**承接口径**，待正式文案/流程签收。不应照抄当时示例的“申诉已结束”而掩盖随后新增的 48 小时最终复核机会。

### 12.5 一次最终复核

**DISP-10｜一次。**用户对首次结果不服，可以申请一次最终复核。[Q85]

**DISP-11｜异人处理。**最终复核必须由不同于首次审核人员的人处理；需要实际人员安排，不能仅在系统里换一个角色名。[Q85]

**DISP-12｜48 小时申请期。**从用户收到首次处理结果起 48 小时内提出。[Q86]

**DISP-13｜暂停结算。**首次违约结果后的复核申请窗口内，暂不将争议 D 结算给餐厅；若用户按期申请，继续保持待处理，直到最终复核结束。[Q87—Q88]

**DISP-14｜复核结果。**翻案应按结果原路退 D；维持违约则按既定归属处理，并再次通知用户。这里的“最终”是平台内部处理结论，不写成排除其他救济渠道的表述。[Q85、Q100]

最终复核**完成**需要多久，未作决定；Q86 的 48h 是申请期限，不是平台完成复核的时限。[OP-11]

### 12.6 期满未申请最终复核

**DISP-15｜自动进入餐厅补偿结算流程。**首次违约结果收到后 48h 内未申请最终复核，期满进入餐厅补偿结算，不再以新增运营审批作为 Q88 已选流程的默认前置。[Q88]

“进入结算流程”不等同于已经确定支付接口、自动分账产品或银行实际到账时刻。具体结算路径、可用资金、账单、失败补偿、责任与凭证仍需设计并批准。[OP-14]

有用户正在按期复核的 D 不得在这一自动流程中结算；复核结果与结算窗口的并发处理，必须有唯一可追踪结果。

### 12.7 流程总图

```text
餐厅标记履约异常
→ D 暂缓退款
→ 平台联系餐厅了解事实、通知用户
→ 用户收到异常通知后的 48h 首次申诉窗口
   ├─ 用户说明：平台审核
   └─ 用户完全不回复：按业务选择默认首次违约〔举证/送达前提待审〕
→ 发出首次处理结果
   ├─ 无违约且应退 D：进入原路退款流程
   └─ 首次违约：D 继续暂不结算，开启 48h 最终复核申请窗口
       ├─ 按期申请：异人复核 → 原路退 D / 维持餐厅补偿
       └─ 期满未申请：自动进入餐厅补偿结算流程
→ 告知处理结果、保留依据与资金记录
```

### 12.8 本节未授权的事项

不允许餐厅标签直接扣款；不允许首轮结果刚出就先把争议 D 结算给餐厅；不把“48h 不回复”改成更短时间；不默默取消最终复核；不把暂缓退款宣称为支付机构提供的正式冻结能力。本文的“冻结/待处理”是业务状态表达，不证明资金存放方式已经核实。

<a id="sec-13"></a>
## 13. 特殊情况例外退款

### 13.1 适用与材料

**EXC-01｜允许申诉。**已正式成团的用户，因突发疾病、航班取消或重大交通中断等特殊情况无法参加，可申请例外退款。[Q31]

这些是对话中的举例，不在本文认定每一种情况都构成法律意义的“不可抗力”，也不据此承诺必然获批。

**EXC-02｜合理证明。**原则上提供能够支持申诉的合理材料，只收完成审核必要的信息。[Q33]

医院凭证等只是讨论举例，不意味着已经批准上传完整病历、诊断、身份证影像或广泛健康档案。允许的最小材料、脱敏、接收渠道、访问权限、保存期限和删除方式必须单独确认。[S1，第 60—70 行；OP-10]

### 13.2 审核结果

| 结果 | 处理 | 来源 |
| :--- | :--- | :--- |
| 获批，运营选方案 1 | F 不退，D 全退 | Q32 |
| 获批，运营选方案 2 | F+D 全退 | Q32 |
| 未获批 | 回到该用户原本适用的普通取消规则；不是统一改判为特殊退款 | Q34 |

**EXC-03｜时间不重算。**保证金归属看原取消受理时间，而不是运营多久后驳回；普通成团后取消若原本 Δ>24h，D 业务归平台；若 Δ≤24h，D 补偿餐厅。[Q34、Q97—Q98]

**EXC-04｜例外审核可裁量的是批准范围。**运营可在 Q32 两种方案间选择，需要原因和依据；不代表可以随意改写所有用户的正常取消档位。

### 13.3 与履约争议区分

特殊情况申诉是“用户要求例外退款”；第 12 节是“餐厅报告履约异常后是否扣保证金”。两者不自动共用全部期限。特殊申请最晚何时提出、材料补交是否计入 24h、是否允许同样的一次异人复核，未明确，不以第 12 节自动补全。[OP-11]

若特殊申请时D已有PLATFORM_RETAINED业务处置或已实际结算餐厅，如何纠正、谁先垫付仍待OP-14；前者不得凭本版直接确认为会计收入。

<a id="sec-14"></a>
## 14. 换餐厅、核心条件变更与用户确认

### 14.1 餐厅更换

**CHG-01｜先征求同意。**已成团并披露餐厅后，原餐厅无法履约，平台可提出替代餐厅，但不能单方替换。[Q92]

变更通知应清楚展示新餐厅、地址、预计消费、已知额外收费及核心变化；不能只写“同区域相近价位”省略实际条件。[Q92 的承接解释；S1，第 38—44 行]

**CHG-02｜明确同意。**用户明确同意则继续；拒绝或确认期限届满未回复视为不同意，F+D 全退。[Q92—Q93]

**CHG-03｜动态确认期限。**依距开始的剩余时间设置，在通知时明确截止时间；不采用全场固定 2h/4h，不把无回复视为默认接受。[Q93]

动态期限的最短长度、临近开始的兜底、送达失败如何处理没有确定，不应允许系统给出实际上无法响应的任意时间。[OP-09、OP-13]

**CHG-04｜原餐厅补偿。**原餐厅应提供额外补偿。由原餐厅承担的金额、形式、是否包括同意替换后继续参加的用户，以及平台先行补偿与向原餐厅追偿的关系待定。[Q92；OP-09]

### 14.2 其他核心条件变化

**CHG-05｜仍须同意。**已成团后，预计消费明显变化、新增最低消费/固定额外费、时间明显变更、包间改大厅等核心条件变化，须获得用户明确同意；不同意可无责退出，F+D 全退。[Q94]

**CHG-06｜预算仅参考与变更不混同。**用户现场自行点单导致消费高于预计区间，适用 Q17 的参考价规则；餐厅/平台主动改变核心服务或新增固定收费，适用 Q94，不可用“预计仅供参考”掩盖。[Q17、Q18、Q94]

**CHG-07｜没有回复不是同意。**Q94 的承接规则保留这一边界。但其他核心变更是否全部使用 Q93 的动态期限、超时后具体如何结束，未逐项选择，需同步方案。[OP-09]

### 14.3 与低人数例外的关系

Q74—Q75 已特别规定：**T-8h 后因成员退出人数低于最低值、餐厅同意继续的场景，只通知，不要求重新确认；用户因此退出按主动取消。**

Q94 后来又选“核心履约条件变化须重新同意”，其列举场景没有直接撤回低人数例外。本文保留低人数为**专门已选规则**，不悄悄改成无责退出；与此同时，通用核心变更条款必须明确该例外与用户看到的最低人数承诺如何衔接，提交专项复核。[OP-07、RV-03]

### 14.4 不得复写历史

变更应保存原安排、替代安排、发起时间、确认截止、用户结果及适用退款；不能只覆盖原餐厅/价格/开始时间，让订单失去报名时依据。[S1，第 38—54、128—134 行]

## 15. 客服、退款时效、注销与隐私边界

### 15.1 客服能力分阶段

| 项目 | 首发决定 | 后续目标/待定 |
| :--- | :--- | :--- |
| 渠道 | 仅微信小程序内在线客服 | 后续扩为小程序客服 + 电话 + 企业微信 |
| 服务时间 | 每日 10:00—22:00，Asia/Shanghai | 暂无变更时间表 |
| 首次人工响应 | 暂不承诺固定时长 | 有稳定能力后可再定 |
| 渠道实际可用性 | 本轮确定的是业务安排 | 上线前需配置并验收，不能声明本次已验证 |

来源：Q95—Q97。

**OPS-01｜客服响应不是业务时钟。**取消、退款、申诉等应记录系统真实受理时间，不能因人工晚读消息让用户落入更不利取消档位。[Q97—Q98]

是否允许一条普通聊天留言直接构成正式取消申请，以及具体如何关联订单，尚须流程明确；不能把客服与正式申请入口的差异隐瞒给用户。[OP-13]

### 15.2 退款时间表

| 场景/节点 | 已确定时限或动作 | 未确定内容 |
| :--- | :--- | :--- |
| 用户提交退款申请 | 24h 内完成审核 | 缺材料、复杂争议是否例外及怎样告知 |
| 审核通过 | 审核通过后的次日统一批量发起 | 每天具体批次几点、失败补批 |

| 餐厅漏确认 | 不自动退；进入运营异常待办 | 最长处理时间、失联兜底 |

**OPS-02｜语义区分。**“已申请”“审核通过”“待批量发起”“已提交渠道”“退款结果未知/处理中”“已退款成功”不应相互冒充。业务展示名称可由产品设计，但不能把审核通过直接显示为已到账。

**OPS-03｜24h 与 48h 的冲突。**Q98 一般退款审核是 24h；履约申诉的用户说明窗口为 48h。如果同一事件被系统同时套入两者，就会出现尚未等完用户说明却要求审核结案。两类适用范围和时限优先级尚未明确，必须在流程中分开评审，不能靠“人工尽快”掩盖。[OP-11]

### 15.3 账号注销

**PRI-01｜可随时申请。**用户可以提出注销，不必先自行证明所有订单已结清。[Q91]

**PRI-02｜先处理未结责任。**存在未结束活动、保证金、退款、餐厅补偿、申诉/复核等，进入注销处理中，这些事项继续履行；结清后完成注销。[Q91]

**PRI-03｜不删除资金事实。**注销不直接删除已经发生的订单、支付、退款、保证金处置及必要审计，不消灭退款或补偿义务。具体保留、脱敏和期限须与实际主体/业务核实。[Q91；S1，第 66—70 行]

**PRI-04｜未选择的操作。**注销申请是否阻止新报名、是否撤回通知权限、能否撤销注销申请、最终完成期限及身份核验方式，本轮没有确认。不得把“可以申请注销”写成所有数据即时自动删除，也不能由注销自动取消现有活动而不告知后果。[OP-15]

### 15.4 隐私说明必须更新的事实

首发必须如实反映：性别必填、手机号必需、时间偏好选填、已去掉的大部分画像、扫码到店记录、餐厅正常/异常确认、两轮争议材料和资金去向；证明材料不等于开放一般健康资料收集。

餐厅能看到哪些用户字段、是否能看手机号、其他参与者看到哪些信息、收集/导出/删除的实际渠道和各类保存期限，本轮没有全部确定。不得直接复用旧字段表而继续宣称采集完整饮食、预算、职业或用户桌型偏好。[Q33、Q39—Q51、Q89—Q91；S1，第 60—70 行]

### 15.5 通知要求归并

已确认或由已选流程必需的通知包括：候补自动转正、已成团、成团失效/恢复、后期人数变化、餐厅替换与核心条件确认、履约异常、首次结果、最终复核结果、取消/退款处理。

**“有通知业务要求”不代表已经批准微信订阅消息、短信、电话或企业微信发送能力。**当前客服渠道仅小程序在线；其他触达方式须按实际配置评审。涉及 48h 倒计时的通知，必须解决“送达”而非只“创建成功”的证据问题。[Q60、Q67、Q74、Q81—Q88、Q92—Q97；S1，第 65 行]

### 16.2 对旧政策交付包的范围变化

旧交付包在本轮之前以“单一服务费、逐笔全额退款、无用户性别画像、用户单桌人数限制”为基础，其中部分还是未批准建议。本轮新增或改变了以下实质范围：

1. **双金额产品及保证金返还/扣留。**正常完成订单后仍有 D 待退款责任。
2. **保证金的两种受益方。**餐厅补偿与特定情形PLATFORM_RETAINED业务保留，不能确认会计收入或与餐费分账混同。
3. **付费候补和自动转正。**正式容量与候补资金义务分开。
4. **自动、逐桌、可逆成团。**不再由运营人工确认作为必经成团条件。
5. **晚报名窗口和用户类别例外。**相同桌状态不必有相同退款结果。
6. **商家扫码/履约确认与两轮争议。**新的操作、通知、审计和资金待处理要求。
7. **性别必填及其内部软用途。**同时移除大部分旧问卷字段。
8. **敏感证明材料与注销处理中。**不得把旧隐私草案直接发布。

这些是业务范围变化，不表示用户已经批准某种 Schema、商户后台、支付拆单、自动分账、托管服务或生产拓扑。
