## 0. 标准与真实签收分开

本文件替换旧稿中“个人桌位偏好为硬条件、平台人工确认成团”等口径。它是餐厅合作标准及逐场签收模板，**不是已签餐厅合同，也不是任何餐厅已提供容量、二维码、联系人或赔偿承诺的证据**。对外餐厅合作合同可引用本稿作为待审附件；主体、费用及责任仍须真正签收。

本标准按业务基线第5—14节及S1交接清单拟定；用户费用/退款口径与[REFUND_POLICY.md](REFUND_POLICY.md)同步。身份/联系方式原件、餐厅账户和用户材料存受控位置，Git仅用脱敏索引。

## 1. RS-V1-01 餐厅准入与角色

| 有权确认的人 | 餐厅负责人、容量和费用确认权限、联络及应急方式 | 不以无权限人员口头安排代替签收 |

<a id="rs-v1-02"></a>
## 2. RS-V1-02 每场五项桌位参数

每场开放报名前由餐厅确认，不由运营自行补数字。

| 参数 | 本场应填 | 规则 |
| :--- | :--- | :--- |
| 最低成团人数 min | 【餐厅填写】 | 正常桌达到此有效人数即自动成团 |
| 目标人数 target | 【餐厅填写】 | 优先目标，不是硬性最低、也不是容量上限 |
| 单桌最大人数 max | 【餐厅填写】 | 单桌不可突破 |
| 本场最大桌数 maxTables | 【餐厅填写】 | 超过不能由运营擅自加桌 |
| 多桌分配策略 | 【餐厅从平台有限标准策略中逐场选择并确认revision】 | 具体枚举待技术设计；平台不默认优先满桌或更多桌达min |

正常须满足 **4≤min≤target≤max≤8**。参数同构时max×maxTables为理论正式上限，还应不超过实际签收总席位。付费候补不计成餐厅已提供的正式席位；不以“候补已付钱”增加上限。

例如最少4/目标6/最多6/两桌：每桌4—6人允许；总正式席位不超过12；不会因为目标为6就把5人桌取消。示例仅解释规则，不是本场默认配置。

运营无权自行修改，变更必须重新得到餐厅确认并留新版本；已售核心条件受影响时同步用户变更流程。标准策略必须可审计，满足min/target/max/maxTables、有效报名顺序及候补FIFO；性别均衡仅软目标。已形成的成团事实不能为重新优化分桌任意拆除。OP-06主体选择已闭合；具体策略枚举与首批分配实现是后续技术设计，不在本稿代选，异构桌型不擅自扩大。

<a id="rs-v1-03"></a>
## 3. RS-V1-03 时间、容量保留与自动成团

| 时点/阶段 | 餐厅及平台必须支持 | 不允许 |
| :--- | :--- | :--- |
| 开放报名前 | 本场预约、桌型、总容量和保留安排有效 | 仅有餐厅准入就认为每场都可售 |
| T-24h前 | 有效正式人数达本桌min即自动成团；可补至max | 强制等到target或运营按钮才算成团 |
| 早期成团又低于min | 重新待成团并补人，名称保留地址隐藏；再达min恢复 | 用“首次成团不可逆”忽略人数变化 |
| T-24h | 不足min的桌失败、剩余有效用户F+D全退；未转正候补同样全退 | 未达target但已达min仍强制失败 |
| T-24h至T-8h | 有效成团未满桌可直接补招；T-24h已有效成团后失效的桌继续合法直接补招至T-8h，达min恢复、补至max | 不恢复候补，不复活T-24h已应成团失败的桌 |
| T-8h及以后 | 关闭所有报名、补位；低人数按RS-V1-06处理 | 因餐厅愿意加人就重启候补或新报名 |

容量保留截止必须覆盖所承诺的决策和实际接待安排；需续保时取得新的有效证据，不拿已过期签收支持收费。正式成员只在F+D完整可信支付成功后生效；未付、失败、UNKNOWN和待付锁位不计min。正式席位临时锁定10分钟，UNKNOWN也到期释放；资金继续恢复，晚到成功全退F+D且不抢位。取消/退款受理何时减少正式成员及其他截止交集仍保留OP-04/05。

<a id="rs-v1-04"></a>
## 4. RS-V1-04 费用与收费前适配

F采用平台默认价+活动覆盖，活动级优先，默认具体金额仍TBD。餐厅逐场提出D，经平台运营审核批准形成有效D版本后才能收费，且D_MIN≤D≤D_MAX；两项上下限数值仍TBD，是有权配置并签收前禁止真实保证金收费的Gate。改价留新版本，不追溯已付款订单，不用示例金额填上线。用户F+D一笔合并支付，后台分F/D记账；付款前分别展示实际F、D和合计，完整成功生效时留价格快照。M由用户直接付餐厅。预计人均消费区间由餐厅确认，仅供参考而非上限。最低消费、包间费、服务费、茶位费及其他可预知固定费用逐项明确；“无”也需餐厅确认，不能因没填就自动为0。

首发不提供专门饮食保障，也不收普通口味画像。需要本场无法提供的专门保障时，**收费前**阻止该安排，不能把“非无限制”留到收款后的成团校验才拦。最小适配方式待OP-10/RV-07，不新增完整病史或信仰证明。

推荐实施核验链（待对当前代码做差分，不表示已实现）：

```text
真实餐厅准入 + 本场有效签收
→ 费用、人数、时段和政策版本可兑现
→ 本人准入及最小服务适配成立
→ 根据正式容量/合法付费候补窗口、本场WAITLIST_MAX判断申请可受理性
→ 服务端收费前核验餐厅D版本、平台审批及D_MIN/MAX Gate
→ F+D一笔完整可信成功后报名/候补资格生效；保留在途与实收事实
→ 逐桌自动成团/候补递补及后续履约
```

真实供给失效，应停止受影响的新收费；已经出站或已收款不得直接删除，应查明并按有效退款规则处置。不要误把正式容量已满解释为所有收款都禁止：在已批准候补范围内，允许明确标识的付费候补，但不能虚构正式席位。

<a id="rs-v1-05"></a>
## 5. RS-V1-05 候补、递补与信息

每场须配置WAITLIST_MAX，有效候补人数<上限才开放，达到上限或未配置时不创建新候补支付；统一默认人数尚未冻结。候补T-24h前FIFO自动转正，餐厅无权指定优先人，平台不能按性别跳队。退出与转正由服务端有效事务顺序唯一生效：退出先则全退并不能再转正，转正先则按正式报名类别取消。主动退出后合法重入视为新申请、取得新序号排队尾。重复申请、未结退款重报、资金暴露及到期后另购交集仍OP-08。

候补未转正主动退出全退，到T-24h未转正全退；之后不恢复候补，有效已成团桌可直接补招，且T-24h已有效成团后失效的桌继续合法直接补招至T-8h。

有有效席位且正式成团即向本人解锁餐厅名称、详细地址。早期成团失效保留名称、隐藏地址，再成团再解锁；不能将一桌成团扩为所有候补及未成团桌都可查看地址。取消/退款/注销等终态可见矩阵待OP-15，实际经营披露须RV-07。

<a id="rs-v1-06"></a>
## 6. RS-V1-06 人数减少与餐厅后期确认

T-8h后不再招新。仍≥min正常举行；低于min时餐厅决定：

| 结论 | 剩余愿参加用户 | 原主动取消用户 |
| :--- | :--- | :--- |
| 无法继续 | F+D全退，并另有运营决定的补偿 | 按本人适用规则，不因后续整桌取消自动全退 |
| 同意以当前人数继续 | 通知实际人数变化，不需二次确认；订单继续 | 按本人适用规则 |
| 同意继续后，另有用户仅因人数少主动退出 | 该用户按本人主动取消规则，不自动无责全退 | 不混同平台/餐厅取消 |
| 未回复/连续有人退出/可能只剩1—2人 | 具体期限、下限和重确认方式未定OP-07 | 不擅自扩张已选例外 |

这可能低于通常4人的配置边界，不能同时对用户保证“任何实际饭局都至少4人”。本例外和一般核心条件变更须共同RV-03评审；保留业务选择，不用餐厅确认代替专项通过。T-24h已有效成团的桌在T-24h至T-8h失效，按DR02-01继续直接补招；T-8h仍低于min才进入本节后期决定流程，不提前搬用低人数接待例外，也不复活T-24h应失败的桌。

<a id="rs-v1-07"></a>
## 7. RS-V1-07 扫码与当晚履约确认

餐厅提供本场签到二维码，用户用小程序扫码，作为到场证据；不等于正常履约已确认。餐厅在饭局结束当晚逐人确认**正常履约/履约异常**。“未确认”是待办，不是违约。

正常履约：平台在活动结束次日统一核对并发起D原路退款，F保留。餐厅漏确认：暂不自动退，次日进运营待办联系餐厅，不直接判断用户未到场。

未选择固定迟到分钟阈值。二维码生成、防远程代签、断网补录、没扫码却实际参加等，由最小技术/运营方案处理；不默认引入人脸、身份证或精确定位。午餐/跨午夜“当晚”、漏确认最长处理期、具体事实标准须OP-12签收。

<a id="rs-v1-08"></a>
## 8. RS-V1-08 异常反馈、平台调查与两轮处理

餐厅可以先标异常，不强制当场完整举证；后续必须配合平台了解原因、事实和必要材料。餐厅没有扣D、决定用户违约、跳过申诉或自行关闭复核的权限。

平台通知用户后，用户收到异常通知起有48h说明期；首次结果收到后有48h申请一次异人最终复核。两种48h不能混为平台必须48h结案。争议D在窗口内及按期复核期间暂不结算餐厅。

48h不回应默认首次违约是业务选择，举证和送达前提尚待OP-13/RV-02；餐厅不能以一条标签配合未读消息直接获得资金。期满未申请最终复核自动进入补偿结算流程，不等于款项已经到账。

<a id="rs-v1-09"></a>
## 9. RS-V1-09 保证金补偿与餐厅责任

| 来源场景 | D业务去向 | 与结算的区别 |
| :--- | :--- | :--- |
| 正常履约、候补退出/到期、成团失败或适用全退 | 用户 | 不属于餐厅可得款 |
| 普通当前有效成团后主动取消，Δ>24h | PLATFORM_RETAINED | 业务平台保留，不退用户、不进该场餐厅补偿；不等同ACCOUNTING_REVENUE，RV-01/06仍待复核 |
| 普通成团后主动取消，Δ≤24h | 补偿对应餐厅 | 原取消时刻判定，=24h归餐厅 |
| 普通/晚报名适用不足8h不退D档、No-show或最终违约 | 补偿对应餐厅 | 争议及最终复核未完不可先付；其他结算时点OP-14 |
| 特殊申诉获批仅退D/两项全退 | 用户 | 已结算后翻案责任OP-14，不能抹旧转账 |

成团失效/重新待成团期间取消按当前未成团状态，Δ≥24h退F+D、8h≤Δ<24h仅退D、0<Δ<8h两项不退。已确定的晚报名例外Δ≥8h仅退D；未覆盖报名类别仍OP-05。餐厅实际结算渠道、账户、周期、凭证、失败重试与翻案机制均未批准。不得据此启动自动分账或把“进入待结算”显示为“餐厅已收款”。餐厅补偿与用户应退款、额外补偿分别记账，不拿同一D同时承担两项付出。

<a id="rs-v1-10"></a>
## 10. RS-V1-10 换店、核心变更与安全协助

原餐厅不能接待，平台提出替代方案，明确变更内容和动态确认截止。用户同意才继续；拒绝/换店期限届满未回复，两项全退。原餐厅还需额外补偿，对象、金额与平台先行处理关系待OP-09写入真正合作约定。

新增固定费用、明显变时间或预计消费安排、包间改大厅等核心变更，必须让用户明确同意，不同意可两项全退。一般变更期限尚未确定，不自动套用换店窗口。T-8h后低人数按本标准专门例外并共同复核。

食品安全、场地关闭、现场秩序或平台故障发生时，先由当值人员协助处理并记录事实；收费退还与其他实际责任分开，不能借用户勾选免责声明推掉自身义务。实际应急联系人、响应期限未填之前，不声称已具备应急值守。

<a id="rs-v1-11"></a>
## 11. RS-V1-11 用户信息与最小操作权限

餐厅需要逐人确认，不代表开放全量资料。签到识别标志、可见字段、是否有受控确认页及身份校验待技术/隐私方案；不得默认显示手机号、openid、完整问卷、特殊证明、限制原因或其他活动名单。

授权只限本餐厅本场相应职责，必须能追溯是谁、何时、对哪一位哪笔订单做了什么确认。受控操作页是候选载体，不意味着首发已批准完整商户后台。实际共享须与PN-V1-06一致。

## 13. 首次收费与存量处理

技术可收费、政策可适用、餐厅本场签收有效、资金渠道和运营能力分别有证据，才可给本场开放收费。任一缺项时拦截受影响的新收费；保留已发生的回调、查询、退款、申诉和客服，不切Mock处理真实款。

文本准入、真实餐厅签收和项目G0—G4分别签收；一次代码测试不能代表餐厅确实留了桌，也不能用一个餐厅签字替代用户核心变更同意。
