## 1. 术语

- **F**：活动服务费。
- **D**：履约保证金。
- **M**：到店餐费，由用户直接向餐厅支付，不进入平台 F+D 收款。
- **T**：该场活动适用的开始时刻。
- **Δ**：取消请求被系统可信受理时距活动开始的时间，即 `T - acceptedAt`。
- **PLATFORM_RETAINED**：D 在业务规则上的平台保留处置；不自动等同于会计收入确认。

# 2. DR-01｜资金、支付与席位生效

## DR01-01｜F + D 一次合并支付，后台分项记账

用户侧采用一笔支付：`本次平台支付总额 = F + D`。后台必须分别记录 F 与 D，不得将总额统一当作服务费。

系统至少要支持：仅退 D；保留 F、退 D；F+D 全退；D 进入餐厅补偿；D 进入 `PLATFORM_RETAINED`；D 已退款后又批准 F+D 全退时只补退尚未退款的 F，不得重复退 D。

M 仍由用户直接支付餐厅。

## DR01-02｜正式报名/候补资格以 F+D 完整可信支付成功为生效条件

只有平台取得 **F+D 整笔完整、可信的支付成功事实**后，报名资格才正式生效。

- 未支付、支付失败、支付结果 UNKNOWN：均不是正式成员。
- 待支付锁位不计入成团人数。
- 完整可信支付成功后：有正式容量则取得正式席位；正式容量已满且候补开放则取得付费候补资格。

不能因为已创建订单、已打开支付页或渠道暂时 UNKNOWN 就计入 `min`。

## DR01-03｜待支付席位锁定 10 分钟

创建需要正式席位的待支付订单后，可临时锁定容量 **10 分钟**。10 分钟为 V1.0 已确认业务参数，不再是 TBD。

## DR01-04｜10 分钟为绝对锁位上限；UNKNOWN 不延长

到 10 分钟时，即使支付结果仍为 `UNKNOWN`，也释放待支付席位。

- 不计正式成员或成团人数；
- 其他合法用户可取得席位；
- UNKNOWN 资金继续查询/恢复，不能直接当失败；
- 后续确认实际支付成功：保留真实实收，不重新抢占席位，不超售，并建立 **F+D 原路全退义务**。

资金恢复与席位资格必须分离。

## DR01-05｜F 定价采用“平台默认价 + 活动级覆盖”

1. 平台级默认 F；
2. 特定活动可配置活动级 F；
3. 活动级 F 优先于默认 F；
4. 付款前展示实际 F、D、F+D；
5. 支付/报名生效时保存价格快照；
6. 后续修改 F 不追溯改变已完成报名订单。

**仍待定：平台默认 F 的具体金额。**

## DR01-06｜D 由餐厅提出，平台审核批准后生效

流程：餐厅针对具体活动提出 D → 平台运营审核 → 批准后形成该场有效 D 版本 → 才允许按该版本收费。

餐厅不能直接改用户收费；平台不能伪造餐厅确认；开放真实收费前必须有有效的餐厅 D 提议/确认和平台审核记录；D 修改形成新版本，不追溯已付款订单。

## DR01-07｜D 必须受统一 D_MIN / D_MAX 约束

平台必须具备 `D_MIN`、`D_MAX`。正常活动的 D 必须满足 `D_MIN ≤ D ≤ D_MAX`。

超出区间不得由普通活动配置直接放行；特殊审批若未来需要，另行设计和授权。

## DR01-08｜D_MIN / D_MAX 数值暂不确定，是收费前 Gate

当前只冻结上下限机制：

```text
D_MIN = TBD
D_MAX = TBD
```

在两者由有权人员正式配置并签收前，不允许启用真实保证金收费。不得自行填写示例金额作为生产默认值。

## DR01-09｜普通正式成团用户 Δ>24h 主动取消：D = PLATFORM_RETAINED

对于普通正式成团用户主动取消：

```text
Δ > 24h
F = 不退
D = 不退
D disposition = PLATFORM_RETAINED
```

`PLATFORM_RETAINED` 仅表示业务处置：不再退用户，也不进入该场餐厅补偿路径；**不得直接等同 ACCOUNTING_REVENUE**。

保证金性质、收入确认、税务、开票、实际收款身份和条款有效性继续保留在 RV-01 / RV-06 专项复核范围。

# 3. DR-02｜成团失效、时间边界、候补与多桌

## DR02-01｜T-24h 至 T-8h 成团失效后继续直接补招至 T-8h

某桌在 T-24h 时已有效成团，但在 `T-24h ～ T-8h` 因成员退出跌破 `min`：

1. 记录成团失效；
2. 不立即终止整桌；
3. T-8h 前继续接受合法**直接报名**；
4. 此阶段**不恢复候补**；
5. 达 `min` 自动再次成团；
6. 可继续补至 `max`；
7. 到 T-8h 仍低于 `min`，停止新报名，进入既有“T-8h 后低人数由餐厅决定是否继续接待”流程。

必须保留 `FORMED → INVALIDATED → RESTORED` 等历史事实。此决定闭合 OP-01 主体选择；OP-07 / RV-03 仍保持原状态。

## DR02-02｜成团失效期间主动取消，按取消当时实际状态判断

历史上曾成团，但取消发生时已经跌破 `min`、当前处于失效/重新待成团，则按照取消当时实际“未成团”状态进入退款时间阶梯。

不得采用“只要曾经成团，就永久按成团后取消处理”。历史事件仍保留用于审计。此决定闭合 OP-02 主体选择。

## DR02-03｜T-24h / T-8h 等号边界正式冻结

普通未成团主动取消：

| Δ | F | D |
| --- | --- | --- |
| `Δ ≥ 24h` | 全退 | 全退 |
| `8h ≤ Δ < 24h` | 不退 | 全退 |
| `0 < Δ < 8h` | 不退 | 不退 |

因此恰好 T-24h：F+D 全退；恰好 T-8h：F 不退、D 全退。

T-24h～T-8h 直接加入已成团桌的晚报名用户：

| Δ | F | D |
| --- | --- | --- |
| `Δ ≥ 8h` | 不退 | 全退 |
| `0 < Δ < 8h` | 不退 | 不退 |

Δ 使用系统可信取消受理时刻，不能因后台处理延迟重算。

## DR02-04｜候补退出与自动转正并发：服务端有效事务顺序产生唯一结果

退出先合法生效：候补资格终止 → F+D 全退义务 → 后续转正不得成功。

转正先合法生效：取得正式席位 → 候补身份终止 → 后续取消按转正后的正式报名类别/规则处理。

不以客户端时间决定；不得同时得到两种结果；必须记录服务端生效顺序和事件证据。具体锁/事务/版本实现由 CTO/Codex 设计。

## DR02-05｜多桌分配由餐厅逐场确认标准策略

平台不全局固定“填满第一桌”或“优先更多桌达 min”。

平台提供**有限、可审计的标准多桌分配策略集合**，每场由餐厅在供给确认中选择并形成 revision。具体枚举名称由技术设计决定。

硬约束：

- 满足 `min / target / max / maxTables`；
- 收费前形成有效餐厅确认；
- 运营不得未经新确认自行改变；
- 性别均衡仅为软目标，不能突破容量、FIFO、有效报名顺序或餐厅规则；
- 已形成的成团事实不能仅为重新优化分桌而任意拆除。

此决定闭合 OP-06 主体选择。

## DR02-06｜付费候补设置每场可配置人数上限；退出重入排队尾

每场支持 `WAITLIST_MAX`：

```text
有效候补人数 < WAITLIST_MAX
→ 候补开放

有效候补人数 ≥ WAITLIST_MAX
→ 停止接受新付费候补
→ 不再为新候补创建支付
```

**当前不冻结 WAITLIST_MAX 的统一默认数字。**

用户主动退出候补后，如候补仍开放、未达上限且满足其他条件，可以重新申请，但视为**全新候补申请**，获得新的 FIFO 顺序并排到队尾，原优先级不得恢复。

此决定闭合 OP-08 关于上限机制和重入优先级的主体选择。
