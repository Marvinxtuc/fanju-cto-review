## 二、正式用户协议必须写清的事项

### 1. 主体、服务与适用范围

- [ ] 写明实际运营主体名称、联系方式、客服渠道、服务时间及投诉途径，不能用虚构主体填充。
- [ ] 产品定位保持“上海本地餐厅兴趣体验工具”。不得许诺社交关系或特定同桌人员特征。
- [ ] 明确平台提供活动组织、报名、订位/排桌、信息通知等哪些具体服务；餐厅负责哪些餐饮服务。
- [ ] 确定首发年龄条件、适用地区及用户资格。不得为了年龄或身份核验直接新增身份证或强实名采集。
- [ ] 如平台与餐厅的责任边界不同于当前业务设想，列明具体影响并评审，不通过一句免责声明解决。

### 2. 费用与订单

- [ ] 服务费/订位费的实际名称、收取主体、金额、包含与不包含项目、凭证或开票方式。
- [ ] 餐费到店自理的含义：支付给谁、点菜与结算方式、是否存在最低消费、包间费、预付餐费或额外费用。
- [ ] 首发是否存在商家押金或不退订位成本；如有，需要与现有全额退款机制和收费性质一起评审。
- [ ] 活动价格以服务端计算为准，用户付款前应看到完整费用说明。
- [ ] 区分“报名成功”“付款成功”“待成团”“成团确认”。付款成功不等于已确定最终桌位。
- [ ] 未成团阶段要有容量保障和明确决策截止时间，不能无限等待。
- [ ] 未付款到期、取消后重报、支付结果未知、订单关闭后实际收款分别怎样处理。

### 3. 履约、变更与行为规则

- [ ] 4–8 人桌位范围，以及用户选择桌数后能否被调整；不能默认以运营操作覆盖用户硬限制。
- [ ] 报名截止、成团决定、餐厅信息展示、详细地址解锁、活动开始/结束的时间口径。
- [ ] 当前地址规则为有效已付、合法成团席位且到 T-24；退款或失去合法席位后应收回访问。
- [ ] 变更餐厅、日期、时间、菜单或主要服务时，用户如何得知、接受或退出退款；不得静默替换核心条件。
- [ ] 用户迟到、缺席、临时退出、影响用餐秩序、被举报或列入限制名单的处理标准、申诉和复核。
- [ ] 黑名单不当然免除平台既有履约或退款义务。
- [ ] 食品安全、餐厅违约、场地不可用、平台故障、不可抗力的通知、协助和资金处置。
- [ ] 活动后反馈及评价的期限、用途和可见范围；当前评价不向其他用户公开。
- [ ] 格式条款中不能用免责条款排除依法应承担的责任，也不能把平台违约一概转嫁用户。

### 4. 协议生效与证据

- [ ] 文本版本、有效时间、适用范围、审批人和归档位置。
- [ ] 费用、退款、隐私等重要条款要在付款前可阅读；明确勾选内容，避免默认同意或隐藏重要条件。
- [ ] 升版后新报名重新确认，历史订单保留当时版本，不追溯降低既有权益。
- [ ] 服务端保存文本摘要、用户确认时间与来源，并能还原当时具体条款。
- [ ] 明确用户协议、退款政策和隐私说明如何组成同一发布版本。现有实现以一个当前 AgreementPolicy 文本/版本为基准；不能假定已有独立隐私同意及其版本记录。

## 三、配套隐私说明必须覆盖的事项

正式协议需配套隐私说明，不能仅写“用户同意隐私政策”。

- [ ] 按实际字段列明：微信登录标识、授权手机号、区域/时间/口味/预算/桌数偏好、补充说明、订单与资金流水、协议确认、反馈/评价、通知、限制名单及审计记录。
- [ ] 逐项说明用途、必要性、收集时点、必填/选填、拒绝后的可用功能。浏览、授权、报名的条件分别说明。
- [ ] 饮食要求中可能含健康或宗教等敏感信息；明确首发允许表达的字段及边界，不引导上传诊断、病史或证明材料。扩大采集须另行评审。
- [ ] 说明历史订单保留报名时问卷快照；修改当前偏好不会自动改变原订单安排。规定联系运营更正原订单需求的流程。
- [ ] 明确运营能看到哪些信息、餐厅是否获得用户信息、其他参与者能否看到；按最小必要范围共享。当前不能承诺“餐厅已能看到完整偏好”。
- [ ] 列出真实采用的微信能力、第三方服务及其处理目的，不能把规划中的订阅消息或其他能力写成已启用。
- [ ] 逐类决定保存期限、到期处置及备份保留期限；资金/审计依法留存与普通偏好删除分开。法定财务留存期限由实际主体和业务性质确认，不凭经验随意填年数。
- [ ] 查询、更正、导出、撤回、注销和删除的入口、核验方式、处理期限及未结订单处理。
- [ ] 注销不得删除已发生资金事实或退款责任；需要最小化、脱敏及合法留存设计。
- [ ] 安全措施只能写实际上线具备的内容；传输、存储、访问控制、日志、备份与应急处置分别验收。
- [ ] 当前尚无完整用户注销/导出/自动到期处置流程。若承诺人工渠道，也必须真实配置渠道、责任人和处置记录，不能把文档承诺当作实现。

## 四、餐厅保障：需要真实确认并留证的事项

### 1. 每家餐厅的供给与履约

- [ ] 确认商户实际名称、经营地址、可核验的经营及食品服务资质、联系人和应急联系渠道。
- [ ] 具体活动的预约日期、时段、桌位/座位容量、4–8 人可用桌型、保留期限和超时释放条件。
- [ ] 是否在正常营业公共环境内用餐，包间/拼桌及其他顾客的安排如何告知。
- [ ] 菜单、预算说明、额外收费、最低消费、菜品售罄或更换规则。
- [ ] 决定前如何锁定餐厅容量，确认后如何避免超订；活动取消、餐厅临时关闭或无法提供桌位如何处置。
- [ ] 客人点菜/付款/开票主体、餐厅迟延或食品问题的现场响应与平台协助路径。
- [ ] 平台与餐厅是否有费用或赔付结算关系；没有经批准的商户后台或自动分账能力，不能在协议中承诺这些流程。

### 2. 饮食保障与桌数偏好

- [ ] 区分普通口味偏好、饮食限制与需要专门安全保障的要求，不把“运营认为可以”当作餐厅证明。
- [ ] 每项可提供保障要写到具体活动/菜单/时段，并记录确认人、确认时间、证据及失效条件。
- [ ] 不承诺无法核实的无过敏原、无交叉接触或严格专用制作环境；不能通过用户免责勾选替代餐厅能力。
- [ ] 无法确认满足要求时，在收费前拒绝该安排；已实际收款的，必须建立可追踪退款/异常处置。
- [ ] 首发是否只接受普通菜单、无特殊饮食保障需求，需要明确决定并在用户付款前告知。
- [ ] 用户接受的桌位人数属于硬约束；若允许调整，必须有具体重新确认流程，不能默默改原订单快照。
- [ ] 保障发生变更时重新校验所有受影响报名，不以“曾确认过”永久放行。

**现有代码缺口：**当前成团校验会阻止任意非“无”的饮食限制和不符合快照桌数的排桌，但没有餐厅能力映射。特殊饮食需求仍可能先付款再被成团校验阻止。不能把这描述为“已经实现收费前核验”或“已支持个性化饮食保障”。政策决定后需补对应本地实施和验证。

### 3. 餐厅签收单建议字段

餐厅/活动 ID；日期时段；可用桌型和容量；菜单及费用；保障项目及限制；确认人与证据；容量保留截止；临时变更通知方式；违约/取消处置；应急联系人；复核人及签收时间。

每场首次收费前必须有有效签收证据；模板存在不能替代真实餐厅确认。

## 五、退款政策：必须决策的规则与执行边界

### 1. 各场景逐项确定

| 场景 | 必须写清 | 当前实现/约束 |
| --- | --- | --- |
| 待付取消或到期 | 是否已出站支付、怎样可靠关单、何时释放容量 | 未知支付结果不能假装失败；关闭后晚到实际收款仍记录 |
| 成团失败/平台取消 | 全额退哪些费用、通知与退款发起时限 | 已有逐笔全额退款义务与持久恢复；到店餐费另属餐厅结算 |
| 用户在 T-24 前取消 | 申请条件、审核规则、是否应全额退、时限 | 当前进入运营审核，不自动退款 |
| T-24 时刻及之后、开始前取消 | 是否全额退、是否允许拒绝及证据、处理时限 | T-24 时刻归“24 小时内”；当前仍经运营审核 |
| 已开始/已完成、迟到或缺席 | 普通申请与服务未履行、餐厅违约的例外分别处理 | 普通用户取消路径在开始后被拒；异常退款的运营入口与能力须专门确认 |
| 餐厅不能兑现安排/保障 | 平台主动处置、用户选择、退款及餐费纠纷协助 | 不能以用户取消条款代替平台违约处理 |
| 订单关闭后收款、额外重复收款 | 每笔真实实收如何保存、原路退回及告知 | 已有独立资金事实与全额退款义务，不恢复旧席位 |
| 渠道结果未知/退款失败 | 显示状态、主动查询、重试和人工升级 | 未知结果保守占款，8 次重试后人工待办，不删除记录 |
| 退款审核拒绝 | 明确拒绝理由、复核渠道、合法订单去向 | 不能机械恢复到已取消/结束活动或失效桌位 |

### 2. 建议供团队选择的首发口径

- 建议：**开始前用户取消可全额退服务费，仍经运营审核**。T-24 前走快速审核，T-24 至开始前加急处理；审核用于核实订单/重复请求及履约处置，不以临近开始为由任意拒绝。
- 成团失败、平台取消、餐厅无法兑现已确认核心安排，服务费全额退。
- 活动已正常履行后的普通缺席原则上不退；未提供承诺服务、错误收费等异常仍需受理并复核，不能写成“一律不退”。
- 上述是建议，**尚未批准或启用**。如选择开始前临近取消不退，需明确客观理由、费用性质、付款前提示及合法性；不能让运营自由决定。
- 首发保留逐笔全额退款，不引入部分退款、余额、代金券替代或额外罚金。若需要部分退款，必须新增资金预算与状态机专项设计。

### 3. 时间、渠道与运营责任

- [ ] 时区采用 Asia/Shanghai；T 相对活动开始时刻计算。判断使用申请被服务端受理的时间，明确边界和活动改期的适用规则。
- [ ] 订单适用哪一版政策必须可追溯，后续改版不能追溯削减权益。
- [ ] 明确客服/审核服务时间、受理及审批时限、批准后发起退款时限、超过时限的升级责任人。
- [ ] 区分“退款获批”“已提交渠道”“退款成功到账”。到账预期须与实际商户/微信渠道规则一致，不编造固定到账保证。
- [ ] 原路退款、原渠道不可用、商户余额不足和退款退回等异常的跟进方式。
- [ ] 审核拒绝、人工处置、异常结案有原因和审计；涉及资金差异的最终结案应异人复核。
- [ ] 退款申请、处理中及成功各阶段是否占容量/保留席位，要与代码状态矩阵一致，不能提前释放尚未明确处理的资金责任。
- [ ] 备份恢复后先双向对账，覆盖渠道有本地无、额外收款、未收敛退款；账单下载失败不能记为零差异。
- [ ] 客诉退款与餐厅现场餐费争议的受理边界、证据、协助和升级渠道。
