## 0. 如何使用本稿

本稿将原来的单一服务费、人工确认成团、个人桌位人数偏好和 T-24h 地址延迟解锁，替换为本轮最终业务决定。正文中的 F 是活动服务费，D 是履约保证金，M 是到店直接支付给餐厅的餐费。符号只是审核表达，不是要求用户面对技术变量。

以下 `PUBLIC_DRAFT_START/END` 仅划定拟向用户展示的范围。当前整篇仍是草案，含待定或专项评审条件，不得直接作为线上 AgreementPolicy。三份用户正文须同包审阅并保留对应全文，不得只上线本协议摘要。

### UA-V1-03 您支付哪些费用

您向平台以**一笔合并支付**支付活动服务费F与履约保证金D，合计为F+D；后台分别记账及处置。F采用平台默认价和活动级覆盖，活动价优先；默认F的具体金额仍待确定。D由餐厅逐场提出，经平台运营审核批准形成有效版本，须满足统一D_MIN≤D≤D_MAX。D_MIN/D_MAX数值尚待有权人员配置并签收，完成前不启用真实保证金收费。付款前分别展示实际F、D及合计；报名生效时保存价格快照，后续F/D改价不追溯已完成报名订单。

到店餐费及已披露的餐厅费用（M）由您直接向餐厅支付，平台不代收餐费。报名页必须展示餐厅确认的预计人均消费区间；该区间仅供参考，不是最终收费上限。现场点菜和结算方式、凭证安排及平台服务包含项目为【待定：OP-03、逐场签收】。

最低消费、包间费、服务费、茶位费等可预先确定的固定收费，应在报名付款前披露。餐厅或平台不得单方临时增加；如提出新的核心条件，应按本协议的变更规则处理，而不是以“预算仅供参考”代替告知。

“服务费全退”仅指F，“保证金全退”仅指D，“两项全退”指F+D，不自动包含您直接向餐厅支付的M。额外补偿与应退款项分开，不以优惠券、余额等替代应退现金。

### UA-V1-04 餐厅桌型与服务适配

正常桌型处于4—8人范围。每场由餐厅确认**最低成团人数、目标人数、单桌最大人数、本场最大桌数及多桌分配原则**，满足4≤最低≤目标≤最大≤8。具体以您付款前展示的本场参数为准，不能把平台4—8人的边界当作所有餐厅都允许任意人数。

您无需选择个人桌位人数范围。平台提供有限、可审计的标准多桌分配策略集合，每场由餐厅选择并形成供给revision；具体枚举是待审技术设计，不在本稿代选。分配须满足min/target/max/maxTables及有效报名顺序、候补FIFO，性别仅为软目标；不得为重新优化分桌任意拆除已形成的成团事实。运营不得自行修改签收参数或策略；重新取得餐厅确认后，如影响已售核心条件，还需按变更规则处理。目标人数是优先目标，不是必须达到的成团门槛。

首发不提供专门饮食保障。明确需要本场无法提供的专门保障时，应在收费前停止该安排，不先收款后再以无法保障拒绝成团，也不要求您改填“无”或勾选自行承担风险以绕过限制。最小适配告知/判断方式须完成【发布阻塞：OP-10、RV-07】；此要求不恢复普通口味问卷或全面健康/信仰资料采集。

<a id="ua-v1-05"></a>
### UA-V1-05 订单、付款与自动成团

提交订单、付款成功、取得正式席位和正式成团是不同结果。只有取得F+D整笔完整、可信的支付成功事实，正式报名或付费候补资格才生效；有合法正式容量则取得正式席位，正式容量已满且候补开放则取得付费候补资格。未支付、失败、UNKNOWN及待支付锁位均不计正式成员或成团人数。

需要正式席位的待支付订单可临时锁位10分钟，这是绝对上限。到期即释放容量，UNKNOWN不延长；UNKNOWN资金仍继续查询与恢复，不直接认定失败。到期后确认实际成功，保存实收并建立F+D原路全退义务，不重新抢占席位或超售。取消/退款受理何时移除正式成员、截止与其他资格事件的交集仍保留OP-04/05。

成团以**具体一桌**为单位：有效正式成员达到餐厅确认的最低人数，立即自动成团，不需要运营再次点击。成团后可继续补至餐厅最大人数；T-24h时达到最低但没有达到目标的桌照常举行。

活动开始前24小时（T-24h）是最终成团检查和候补截止。T-24h前，已成团桌因成员退出跌破最低人数，可重新待成团并补人；再次达到最低则重新成团，到截止仍不足则剩余愿参加用户两项全退。

T-24h至T-8h，有效已成团且有空位的桌接受新的直接报名。T-24h时已有效成团的桌在此窗口因退出跌破最低人数，记录失效并继续接受合法直接报名至T-8h，不恢复候补；再达最低立即恢复成团，可补至最大人数。到T-8h仍不足，停止新报名并进入餐厅低人数继续接待决定流程，OP-07/RV-03仍未通过。此路径不复活T-24h已应失败的桌。

曾成团、取消时已经失效/重新待成团者，按系统可信受理取消时的实际未成团状态进入退款阶梯；历史保留，但不能永久按“曾成团”扣费。恰好T-24h报名分类、失效桌新加入者是否适用晚报名例外仍须OP-05闭合。

<a id="ua-v1-06"></a>
### UA-V1-06 付费候补

正式容量满额后，在本场候补开放且有效候补人数<WAITLIST_MAX时，您可通过一笔F+D完整可信支付取得候补资格。每场必须配置有效人数上限；未配置或人数已达上限时，不为新候补创建支付。统一默认人数尚未冻结，不以无限候补代替配置。候补须清楚标识，平台不把付费凭证描述为已成团或已安排桌位。

T-24h前有合法席位时，按有效候补先后顺序自动转正并通知，无须再次确认。性别均衡、餐厅指定或新报名均不得越过有效队首。退出与转正竞争由服务端有效事务顺序产生唯一结果：退出先合法生效，资格终止并全退，后续不得转正；转正先合法生效，候补身份终止，后续取消按正式报名类别/规则处理。不得以客户端时间决定或同时产生两种权益。FIFO时钟/同刻稳定排序等未覆盖细节仍属OP-05。

**只要仍处候补状态，您主动退出即两项全退。**主动退出后，在候补仍开放、未达上限且其他条件满足时可重新申请；这是全新候补申请，取得新FIFO序号排到队尾，不恢复原优先级。到T-24h仍未转正的候补自动结束并产生F+D全退义务，之后原队列不恢复。资格结束不等于瞬间到账。候补资金暴露上限、重复申请/未结退款重报以及到期退款后另购晚报名席位的交集仍保留OP-08，不擅自推定。

### UA-V1-07 餐厅信息与地址

【承接口径待签收】首次尚未正式成团时，不展示具体餐厅名称和详细地址。您取得有效桌位并正式成团后，**立即展示餐厅名称和详细地址，不等T-24h**。

曾成团后又重新待成团，餐厅名称保留，详细地址重新隐藏；再次成团重新解锁。一个活动的其他桌成团，不代表您所在的未成团桌或候补身份获得相同权限。隐藏仅影响后续展示，不能抹除已经看到或截图的信息。

<a id="ua-v1-09"></a>
### UA-V1-09 非本人责任、特殊情况及额外补偿

普通最终未成团、候补到期未转正，两项全退；这两种情形没有统一额外补偿承诺。因平台或餐厅原因取消，无论是否已成团，两项全退并另给补偿，补偿方案由运营决定，不能代替应退款项，也不能把“人工决定方案”理解为可以完全不给已承诺的补偿。

已成团后因特殊情况不能参加，可以凭合理必要证明申请例外退款。运营审核通过，可选择仅退D或两项全退；未通过则回到本人原适用规则，使用原取消时间，不因审核延迟重算归属。不授权任意比例、额外罚金或只退F不退D等新的例外方案。

举例的疾病、航班或交通事件不等于平台事先认定其均属法律意义的不可抗力；证明材料范围、渠道与保护方案见【发布阻塞：OP-10/OP-11、RV-05】。具体申诉与履约争议是不同流程，不自动共用全部期限。

<a id="ua-v1-10"></a>
### UA-V1-10 T-8h后人数减少的专门规则

T-8h后不再招募。因成员退出使人数低于餐厅最低值，由餐厅确认是否按当前人数继续：不继续时，剩余愿参加用户F+D全退并有额外补偿；导致人数不足的主动取消者按其自身规则处理，不因后续整桌取消自动全退。

餐厅同意继续时，平台通知实际人数变化，**不要求剩余用户再次确认**；用户因人数变少而退出，仍按其本人主动取消规则处理。这是Q72—Q75保留的专门例外，不被一般核心条件变更条款悄悄覆盖。

最低还能有几人、连续退出、餐厅不回复的截止处理以及对外承诺衔接尚须【发布阻塞：OP-07、RV-03】。不得一边宣传“所有实际饭局永远至少4人”，一边启用本例外。

<a id="ua-v1-11"></a>
### UA-V1-11 到店、餐厅履约确认与保证金退还

用户在餐厅使用小程序扫描本场签到二维码，形成到店记录。扫码成功不等于正常履约已确认，也不立即退保证金。

餐厅须在饭局结束当晚确认“正常履约”或“履约异常”。正常者F保留，D在活动结束次日由平台统一核对并发起原路退款。餐厅当晚未操作，暂不自动退，进入运营待办联系餐厅；漏确认不能直接认定用户违约。

餐厅可以先标异常，再由平台了解事实，但没有直接扣保证金的权力。餐厅确认载体、二维码和未扫码补证、当晚具体截止、漏确认处理期限及具体违约标准仍须【发布阻塞：OP-12】落实，不新增固定迟到分钟数或商家一键扣款。

<a id="ua-v1-12"></a>
### UA-V1-12 履约异常、48小时说明与一次最终复核

餐厅报告异常后，D暂缓退款，由平台了解餐厅事实并通知用户。用户收到异常通知后有48小时提交说明，窗口内不得提前形成最终扣除结论。

【发布阻塞：OP-13、RV-02】按已选业务规则，48小时完全不回应将默认首次认定违约、D不退；但“收到”的证据和餐厅证据不足时的前提尚未审定，**该规则当前不得直接启用为自动扣款**。本稿保留选择，不把它改成另一种规则，也不把消息创建当送达。

首次处理结果须通知用户。收到首次结果后48小时内，可申请一次由不同审核人员处理的最终复核；申请窗口内及按期复核期间，争议D不先结算给餐厅。复核翻案按结果原路退D并通知；维持违约按对应规则处理。48小时申请期届满未申请，自动进入餐厅补偿结算流程，不等于已完成真实转账。

首次结果的具体展示字段属于承接口径待签收；平台完成复核的期限、结算与翻案资金路径见OP-11/OP-14。平台内部最终结论不表述为排除其他适用救济。

<a id="ua-v1-13"></a>
### UA-V1-13 餐厅更换及核心条件变化

餐厅更换须提出明确替代方案，用户明确同意后继续；拒绝或动态确认期限届满未回复，视为不同意，F+D全退。期限根据距开始的时间设置并随通知说明，不默认为固定2小时或4小时。原餐厅另有补偿责任，其承担对象、标准和先行处理关系待OP-09签收。

其他核心条件如餐厅主动明显改变消费安排、新增固定收费、明显改用餐时间或包间改大厅，也须明确同意，不接受可两项全退。现场自主点菜超预计预算与餐厅主动变更不是同一事件。一般核心变更的超时收口、改期后用原T还是新T、补偿细则尚待OP-09；不得将Q93换店期限自动扩到所有变更。

T-8h后的低人数情形按UA-V1-10专门规则处理，其与本条的说明须共同评审。变更不覆盖报名时旧条件、价格、政策、用户确认和受理事实。

<a id="ua-v1-14"></a>
### UA-V1-14 退款进度与时间

一般用户退款申请在系统受理后24小时内完成审核；获批后的**次日**统一批量向原支付渠道发起。次日按Asia/Shanghai下一个自然日理解，具体批次尚待确定。正常履约退D使用活动结束次日的专门链路，不机械再额外等待一个一般审核周期。

“申请已受理、审核通过、待批量发起、已提交渠道、结果未知/处理中、退款成功”是不同进度，实际到账以渠道处理结果为准，不承诺固定到账时长。

一般24小时审核与履约48小时说明/复核窗口的适用衔接、自动退款义务是否另需审核、漏批和复杂事项期限须【发布阻塞：OP-11】确定，不能为了赶一般审核时限跳过用户说明。

原渠道客观不能退款时，进入人工异常处理；不能擅自转平台余额或用优惠券替代应退现金。10分钟锁位释放后晚到成功款建立F+D原路全退义务并保留事实，不抢回席位；重复额外实收与未知结果仍须保留、查询并追踪，不用删除记录结束责任。

<a id="ua-v1-15"></a>
### UA-V1-15 注销、反馈、秩序与责任

用户可随时申请注销；如尚有活动、保证金、退款、餐厅补偿、申诉或复核，进入注销处理中，相关责任继续处理，结清后完成注销。注销不抹除已发生的资金和必要审计事实。具体权利入口、时限、共享和留存见同版本《隐私说明》，不能承诺未建成的一键注销或即时全部删除。

平台和餐厅分别就实际承诺与承担的服务处理问题，不以“自愿参加”等文字代替自身责任。餐厅异常标签、举报或限制名单，不当然消灭已有退款及履约义务。反馈/评价沿用交接清单中不向其他用户公开评价的范围约束，具体时窗和限制标准不在本轮新增天数，须核对当前批准记录。
