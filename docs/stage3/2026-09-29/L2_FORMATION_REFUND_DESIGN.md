## 依赖与唯一写入规则

L2 必须在 L1 的 `registrationActive`、`capacityHeld`、订单版本及统一状态写入 helper 完成之后切换。所有影响候选集合的报名、付款、到期、取消、退款与成团，在事务内先锁 Activity，再按稳定顺序锁相关 Order；需要资金校验时接着锁 Receipt。任何外部渠道请求都在事务外，返回后重取锁和版本。`GROUPED` 活动不能因晚到付款重新分配旧桌位。

以 **已确认收款事实**为资金来源，以 **当前有效订单和已确认 TableMember** 为履约来源。活动状态本身不能证明某个用户有席位。成团决策前，已收款且等待成团必须仍有容量保障及明确决策截止时间；决策后每笔实收要么有合法履约，要么有按原 receipt 关联、可追踪的退款或人工异常处置。额外或晚到收款分别处理，不互相抵扣。

## 草案与成团事务

1. 在 Activity 锁下读取 L1 定义的有效、已确认付款候选集合；排序固定为创建时间及订单 ID。待核查收款不自动加入候选。记录候选集合摘要与草案版本。
2. 首次建草案、人工调整和重建使用相同成员校验：每人至多一桌，每桌满足本活动人数上下限，提交成员集合与当前完整候选集合相等。六人取消一人后，旧草案标为 `CANCELED`，保留成员和审计；五人仍满足规则时生成新草案。禁止通过删除旧组来隐藏历史。若不足最低人数，走失败决策并建立退款责任。
3. 确认时重新锁定 Activity 与候选订单，校验版本、集合摘要、人数、成员状态、重复成员及每笔收款去向。当前集合与草案不同，返回可重建的冲突结果，不能确认旧草案；此时无订单/活动状态变更。
4. 同一事务确认桌组、订单及活动状态，写审计，并为每个接收人建立唯一业务键的通知待投递记录。通知失败只影响投递状态，不撤销已提交的合法成团；worker 按持久任务重试。重复确认必须返回同一决策，不重复建桌、退款或通知。
5. 成团失败和运营取消逐笔核对 receipt、既有退款与义务，在同一事务建立尚未结清的退款责任和任务。对于已存在 REVIEWING、REFUNDING、UNKNOWN 的退款，先预留或复用原预算；不能再生成冲突的全额退款。长批次可由持久任务分批处理，活动先进入不可新报名状态，每笔责任有负责人、截止时间和可恢复游标。

### 基于 L1 Schema 的迁移边界

当前 `TableGroup` 只有活动、状态和成员，`Notification` 没有唯一业务键。L2 本地迁移拟增加 `TableGroup.generation`（历史默认 0）、`candidateDigest`（历史为 NULL）、`ordinal`（历史为 NULL），以及 `Notification.businessKey`（历史为 NULL、唯一）。新增草案必须为同一代写入候选订单 ID/版本的排序摘要及从 1 开始的桌序；数据库约束保证同活动、同代、同桌序唯一。活动行锁串行分配下一代，不能仅凭 `createdAt` 猜最新草案。历史 NULL 摘要的待确认草案一律要求重新核对或重建，不能直接确认；历史已确认桌组及其成员保留，不能因回填而删除。唯一业务键使同一成团决策的站内通知可重试且不重复落行。

迁移先 expand、检查历史草案和重复通知、再切读写；不删除旧组、成员、收款、退款与通知记录。精确 SQL 和兼容组合在实施时以当前 Schema 生成并用隔离 PostgreSQL 验证。失败只停止新成团，保留存量处理。回退版本须用实际提交 SHA、API/worker/数据库组合及演练结果证明；当前 `bc25f5b` 不可宣称兼容。

## 退款政策与拒绝后去向

`evaluateRefundDecision` 已定义用户在活动开始前 T-24 两侧均进入人工审核、开始后拒绝，以及成团失败或运营取消全退。L2 路由要以事务内重新读取的活动时间和状态调用这一政策。运营取消应有专用受控入口与审计；当前仓库未找到该入口，不能把 mark-group-failed 充当所有运营取消。

| 事件和当前事实 | 订单与席位 | 资金及补偿 |
| --- | --- | --- |
| 用户申请取消，尚未开始 | `REFUND_REVIEWING`；旧草案需失效重建 | 保留原 receipt，逐笔预算待审批；在审批前继续遵守 L1 占位规则 |
| 退款审核拒绝，仍可报名且容量保留 | `PAID_PENDING_GROUP`；不恢复旧草案 | 审计拒绝原因；未结清义务不能因拒绝消失 |
| 拒绝时已有有效确认桌位 | `GROUPED`，关联当前有效桌位 | 只有收款仍未退且无其他未决退款才恢复履约 |
| 拒绝时活动已取消、成团失败或桌位失效 | 不机械回到已付/已成团；禁止地址 | 逐笔原 receipt 建退款/异常责任，人工待办有负责人和期限 |
| 审核期间活动已完成、用户已到场或退款未知 | 保留完成和资金事实 | 先查履约及渠道；不得用旧审核结果覆写较新状态 |
| 决策后晚到或第二笔收款 | 不复活关闭单、不强塞旧桌 | 记录真实流水，分别形成全额退款义务或异常处置 |

退款审核拒绝的 API/运营 UI 当前也缺实现，L2 应增加受控路由、并发条件和审计；不能仅靠数据库改状态。收款预算以 receipt 为边界，已成功、处理中、UNKNOWN、MANUAL 均按保守占款。完成或失败回调只通过 A2 状态机应用。

## 地址与用户操作

订单详情先验证本人；只有订单处于合法已成团后状态、活动处于允许展示状态、存在属于本订单且未取消的当前 `CONFIRMED` TableGroup/TableMember、当前时间达到 T-24，才返回地址。只有时间未到时可返回餐厅名称；无有效桌位时连餐厅详情也按最小信息处理。后台候选和桌位读取按角色授权，不把其他用户问卷或手机号写入普通用户响应。

用户订单页沿用 U1 服务端刷新、取消申请与退款进度；`paymentState=REQUIRES_REVIEW` 时不能续付。政策拒绝、成团失败退款待办、通知失败均要有明确用户状态和运营处理入口。运营动作写入审计，日志不包含收款凭证或完整手机号。

## PostgreSQL 故障验收矩阵

| 场景 | 断言 |
| --- | --- |
| 六人草案后取消一人 | 旧草案仍在且取消；五人新草案可确认；每人一桌，无遗漏或重复 |
| 草案后新增合法付款或到期关闭 | 旧集合摘要失效，确认拒绝；重建纳入当前完整集合 |
| 取消、付款、成团确认三方并发 | 锁顺序无死锁；每笔实收有席位或明确责任；不出现同一订单双桌 |
| 成团失败/运营取消中途杀 worker | 逐笔义务及任务在库；重启后补齐，重复执行不超额退款 |
| 通知落盘失败 | 成团事务整体失败；ACK 后投递失败则任务可重试，不重复发给同一业务键 |
| 无桌位但活动已成团，到 T-24 | API 不返回地址；有有效桌位且到时才返回 |
| 退款拒绝与取消/完成/桌位失效交错 | 仅按新事实合法去向；保留已发生的退款和收款 |
| 已有部分退款、UNKNOWN 退款或第二笔收款 | 按每个 receipt 的剩余预算建立责任；不超额、不丢额外收款 |

每项使用隔离 PostgreSQL、真实 API/worker 路径和可定位断言；不得为全绿跳过数据库或删除旧断言。还须重新生成实际 API/worker、ops、weapp 产物，验证发布包独立启动，并在小程序本地模拟器完成与 API 连通的用户路径。真实设备、微信身份/支付/退款和生产门禁仍分别验收。
