# L2 成团、取消与退款恢复：最小实施任务单

2026-09-29。L2 本地专项待确认，未实施、未放行。L1 统一订单占位字段/锁协议及 A2 资金事实、预算、任务机制已在隔离工作副本实施。不得并行另建一套订单状态写入规则。精确事务、资金责任、通知与验收边界见 [L2 设计准入稿](L2_FORMATION_REFUND_DESIGN.md)。

## 已核实的断点

- app.ts生成草案发现任意旧tableGroup就返回existing；人数变化后无法从失效草案恢复。
- 确认成团只检查草案成员，不检查当前全部有效已付集合；活动级成团不足以证明每笔已付订单有合法席位。
- 当前GET订单的地址展示使用订单/活动状态与时间，没有确认有效TableMember。
- evaluateRefundDecision已定义T-24两侧、开始后拒绝、成团失败/运营取消全退，但用户取消路由仅检查订单状态。
- 当前确认成团提交事务后再写通知，通知失败没有可靠补发；应复用持久事件任务。
- 当前 `mark-group-failed` 明确记录 `automaticRefund: false`，只变更活动和订单状态，未建立已收款退款义务；仓库内也未找到独立的运营取消及退款审核拒绝入口。

## 退款审核拒绝后的事件矩阵

| 当前事实 | 资金事实 | 订单合法去向 | 席位/补偿 |
| --- | --- | --- | --- |
| 活动仍报名中且有效占位保留 | 实收未退、无其他未决退款 | PAID_PENDING_GROUP | 保留容量等待明确成团截止，不恢复旧草案 |
| 活动已成团且本人有当前确认桌位 | 实收未退 | GROUPED | 只恢复当前仍有效的桌位关联 |
| 活动已成团但桌位已失效 | 实收未退 | 待异常处置，不机械GROUPED | 禁止地址解锁；新建有负责人/截止时间的处置，合法补排或退款 |
| 活动取消或成团失败 | 实收未退 | 退款责任处理 | 拒绝用户申请不能消灭平台退款义务；原receipt逐笔核算剩余预算 |
| 活动完成或已到场 | 核对实际履约及实收 | 不回退为待成团/已成团 | 保留完成事实；异常退款须独立审核，不能复活旧桌位 |
| 已有成功退款或结果未知 | 保留成功/未知事实和预算 | 不能用拒绝覆盖资金事实 | 先查询/对账，完成责任核验后决定下一步 |

精确订单状态、草案版本字段及迁移将与L1最终实现对齐后冻结；以上不能作为已通过Schema评审的替代。每包执行前记录具体授权；本任务单不授权生产数据、真实渠道外发或修改已批准的退款政策。
