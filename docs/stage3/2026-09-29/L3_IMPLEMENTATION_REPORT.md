# L3 本地实施记录

日期：2026-09-29。工作副本 `codex/fanju-stage0-baseline`，改动尚未提交。用户在 L2 完成后要求“继续”，本轮按 L3 设计实施隔离数据库与 mock 路径；未访问真实微信或生产环境。

## 已实施

- 增加 `AgreementPolicy` 历史版本表与唯一当前版本约束。服务端从数据库时钟读取当前生效版本，并校验文本摘要；未配置、未到启用时间或摘要错误时停止新协议确认和新报名。小程序读取服务端当前文本，用户勾选后提交其版本。旧版、虚构版或未签收当前文本不能建立新订单。
- 同意记录保存协议文本摘要。订单在活动事务内重读当前协议及该用户同意记录，保存其引用。历史订单保留原版本；既有待付订单可按原 L1 复用逻辑找回。
- 新订单必须有完整的服务端问卷档案。订单只保存排桌必要字段与规则版本，不保存自由备注。运营候选读取订单快照，用户之后更新资料不会改写已建订单。
- 排桌草案、人工调整和确认均核对订单快照。桌数偏好不兼容或饮食限制缺乏餐厅能力证明时返回明确阻断原因，并生成有负责人和期限的人工待办；没有业务批准的例外通道，不能绕过饮食限制自动确认。运营候选展示饮食限制。
- 自动桌型冲突后，运营仍可在报名开放或锁定阶段提交满足全部硬约束的首个人工方案；合法方案保存时关闭先前的桌型核查待办。活动取消时，缺少可信收款回执的历史已付订单建立持久资金核查工单，避免订单停在退款中却无人处理。
