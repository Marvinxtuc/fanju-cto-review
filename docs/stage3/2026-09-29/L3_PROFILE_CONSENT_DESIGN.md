# L3 报名前置问卷与协议版本：本地设计准入稿

2026-09-29。F17/F18 是原审计的收费上线前 P1，验收位于 G3。本文是代码核查后的接口和验收提案，未实施或获专项批准；实际席位地址授权先由 L2 满足 G1。L3 与 L1 的订单重报及 L2 的桌位候选快照共用订单事务，不建立另一套报名写入。

## 已核实的断点

- `POST /api/orders` 只检查手机号和客户端传入的 `agreementVersion` 是否有同字符串 ConsentRecord；不要求 UserProfile，也未填充已有的 `Order.profileSnapshot`。
- `POST /api/consents` 接受任何非空版本；客户端仍以固定字符串提交。仓库未设服务端当前协议版本与获批文本摘要。
- 草案按报名创建时间切分，`table-candidates` 展示的是当前 Profile；用户改资料会改变运营看到的偏好，却不能还原报名时条件。
- `evaluateTableFormation` 只计算人数和桌大小。`dietaryRestrictions`、`acceptableTableSizes` 尚未形成可执行的硬约束；把所有问卷字段直接当成硬限制会改变业务政策，需要产品明确。

## 协议契约

服务端维护唯一当前生效的协议版本、获批文本摘要、启用时间及政策来源。客户端先读取当前版本和文本，再提交同意；同意接口校验版本确为当前版本，保存用户、版本、摘要、时间、来源及服务端记录 ID。创建订单在 Activity 锁内重读当前版本和同意记录，要求二者一致，订单保存该版本及同意记录引用。协议升版不修改历史订单；旧版或伪造版本返回可辨识的“需重新阅读并同意”，不能由客户端自动补写同意。

这会增加配置或 Schema 与公开读接口；具体位置应以获批协议文本的发布方式决定。正式文本、摘要和启用时点没有提供时，不能凭 `v1` 或测试占位字符串宣称真实协议已签收。配置快照要能让多实例在切换期间一致；旧、新客户端组合列入版本矩阵。

## 问卷和候选快照

创建订单在同一事务读取经服务端校验的必要 Profile，保存最小不可变快照及规则版本；缺失、字段非法或未满足活动必要条件即拒绝，不占容量、不建支付意图。快照只包含排桌所需字段，避免自由备注或不必要个人信息进入运营列表、日志和通知。用户后续更新 Profile 只影响新订单；旧订单快照及其校验依据保留。

草案与确认均使用订单快照，不再读取用户当前 Profile 作为决策事实。`acceptableTableSizes` 与每桌人数必须相容；饮食限制应先经产品确认可表达的菜品/餐厅保障范围，无法证明满足的硬限制必须阻止自动确认并进入有理由、责任人及复核人的人工例外。地区、时间、口味、氛围等字段哪些属于硬条件要逐项决定；不能把缺少餐厅能力数据的字段当成“已通过”。人工例外不得悄悄覆盖安全或饮食禁忌。

## 最小实施切片与验收

| 切片 | 文件和操作 | 必要证据 |
| --- | --- | --- |
| L3a 协议基准 | 服务端当前协议配置/读接口、`/api/consents`、`/api/orders`、小程序同意页 | 旧版、虚构版、未同意拒绝；升版后新订单需新同意，旧订单保留原记录；并发切换无错配 |
| L3b 问卷快照 | `app.ts` 下单、`Order.profileSnapshot`、运营候选读取 | 无问卷拒绝且不占位；资料变更不改历史快照；跨用户读取拒绝；无额外敏感日志 |
| L3c 偏好规则 | shared table rules、L2 草案/确认、运营例外审计 | 桌人数硬冲突不自动确认；饮食硬冲突无证明时阻止；合规人工例外可追溯且不可覆盖禁忌 |

使用隔离 PostgreSQL 验证真实写入、事务回滚、历史快照和 L1 重报；测试不能只镜像 helper。API、小程序和运营端需实际构建并核对相同协议契约。真实用户文本批准与生产发布另行验收。

## 待定业务输入

需项目负责人提供获批协议文本/版本及启用规则、饮食限制与餐厅可承诺能力的映射、桌数偏好是否允许例外。没有这些输入时可完成接口与失败路径设计，不得将未知政策编成默认通过规则。
