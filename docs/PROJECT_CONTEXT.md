# PROJECT_CONTEXT

## 1. 项目摘要

本项目是一个面向上海本地用户的微信小程序 MVP，产品定位为“上海本地餐厅兴趣体验工具”。用户通过小程序报名周末或指定时间段的小型约饭局，平台以餐厅体验、兴趣偏好、区域、时间、预算和饮食限制为核心组织 4-8 人餐桌。

项目不做泛人群陌生人交友，不做相亲，不做约会，不承诺匹配对象。对外表达必须围绕“餐厅体验、约饭局、同城活动、兴趣餐桌、周末两小时体验”。

已有决策：

- 首发场景：约饭局。
- 产品定位：“上海本地餐厅兴趣体验工具”。
- 支付：MVP 接入微信支付测试环境或测试商户号；生产真实支付进入上线前独立审批里程碑，见 `docs/PAYMENT_PRODUCTION_REVIEW.md`。
- 退款：成团失败自动全额退款；用户在 T-24 小时以前取消进入运营快速审核；24 小时内取消默认不退款，运营可人工审核。
- 费用：票价仅为活动服务费/订位费，不包含全部餐费；支付金额必须由服务端计算。
- 状态机门禁：后续真实微信支付、退款、登录和手机号接入不得绕过现有 API 状态机 helper。
- Provider 配置：`AUTH_PROVIDER`、`PHONE_PROVIDER`、`PAYMENT_PROVIDER`、`REFUND_PROVIDER` 只允许 `mock` 或 `wechat`；生产环境默认禁止 mock payment，除非显式配置允许。
- 实名与手机号：MVP 必填微信登录 + 手机号；默认不强制实名和身份证；如采集身份证、实时定位、通讯录、私信等敏感能力，必须先完成 `docs/COMPLIANCE_REVIEW.md`。
- 匹配人数：每桌标准 6 人，运营可调整为 4-8 人；少于 4 人不成团。
- 匹配方式：MVP 使用规则引擎 + 运营人工确认；不接入 LLM 或复杂 AI Agent。
- 后台：MVP 做运营后台，不开放商户后台；商户信息由运营维护。
- 地点解锁：付款后展示活动日期、时间段、区域和主题；成团后展示商户名称；活动前 24 小时展示详细地址和导航。
- 项目文档：长期项目，需要 `PRD.md`、`Codex_Brief.md`、`docs/PROJECT_CONTEXT.md`、`AGENTS.md`。

## 3. 项目类型

- 主类型：移动应用。
  - 微信小程序是用户主入口。
- 次类型：API 服务。
  - 需要订单、支付、退款、排桌、权限和数据持久化。
- 次类型：内部工具。
  - 运营后台是 MVP 必需交付物。
- 次类型：后台任务 / 数据处理系统。
  - 需要锁单、排桌、地址解锁、退款重试和通知重试。

不要默认这是普通 Web 项目。不要按“前端 / 后端”机械拆分，应按业务状态机和责任边界拆分。

## 4. 关键用户和使用场景

### 普通用户

- 浏览上海本地约饭活动。
- 登录并授权手机号。
- 填写约饭偏好问卷。
- 报名并完成测试支付。
- 查看订单、成团状态、地点解锁信息。
- 取消订单、查看退款状态。
- 活动后评价或举报。

### 运营人员

- 维护餐厅资料。
- 创建活动批次。
- 查看报名和订单。
- 运行规则排桌并人工确认。
- 处理退款、举报和黑名单。
- 查看审计日志。

### 超级管理员

- 管理后台账号和权限。
- 查看全局审计。
- 处理高风险异常操作。

### 商户 / 餐厅

- MVP 不登录系统。
- 由运营录入和维护餐厅信息。
- 不直接查看用户个人信息。

## 5. 核心功能和验收标准

核心功能引用 `PRD.md`：

- 微信登录与手机号授权。
- 用户协议和隐私确认。
- 结构化问卷。
- 活动列表和详情。
- 订单创建和库存锁。
- 微信支付测试接入。
- 退款规则和退款流程。
- 餐厅管理。
- 活动批次管理。
- 规则排桌和人工确认。
- 信息解锁和倒计时。
- 通知与提醒。
- 评价、举报与黑名单。
- 运营后台权限和审计。
- 文案合规与禁用词检查。

关键验收标准摘要：

- 未登录、未授权手机号、未确认协议用户不能报名。
- 同一用户同一活动只能有一笔有效订单。
- 支付金额由服务端计算。
- 支付和退款回调必须幂等。
- 每桌默认 6 人，运营可调整为 4-8 人，少于 4 人不成团。
- 成团前不展示商户名称和详细地址。
- 成团后展示商户名称。
- 活动前 24 小时展示详细地址和导航入口。
- 成团失败自动全额退款。
- T-24 小时内取消不自动退款，进入运营审核。
- 被黑名单用户不能报名。
- 用户可见文案不得出现交友、相亲、约会、脱单、匹配对象、陌生人交友、CP、找对象等禁用词。
- 高风险后台操作必须审计。

## 6. 非目标、禁区和待审批高风险范围

本阶段默认不做：

- 不做交友、相亲、约会、脱单、匹配对象定位；如需变更，进入高风险待审批范围。
- 不做私信、好友、通讯录、关系链；如需变更，进入高风险待审批范围。
- 不做商户自助后台。
- 不做自动商户分账。
- 不做生产真实支付直接上线；如需变更，先完成支付上线评审。
- 不做强实名认证、身份证、自动投保；如需变更，先完成合规评审。
- 不做实时定位和精确住址采集；如需变更，先完成合规评审。
- 不做 LLM、RAG、复杂 AI Agent 或模型输出。
- 不做多城市、多语言、独立 App。
- 不做诱导分享、裂变红包或平台规则高风险增长机制。

待审批高风险范围：

- 生产微信支付接入：必须完成 `docs/PAYMENT_PRODUCTION_REVIEW.md`，且真实密钥、商户号、证书、token 不得提交到 Git。
- 交友/相亲/约会/脱单/匹配对象等定位或用户可见文案：必须先更新 PRD、文案策略、审核风险说明和验收标准。
- 身份证、实时定位、通讯录、私信、真实用户数据：必须完成 `docs/COMPLIANCE_REVIEW.md` 中的数据最小化、单独同意、权限说明、保存期限、删除/导出机制、日志脱敏和审计要求。

Codex 不应碰：

- 产品定位，除非已有高风险变更审批。
- 用户隐私采集边界，除非已有合规评审和人工审批。
- 退款规则。
- 支付金额和回调状态机，除非已有支付上线评审和迁移方案。
- 权限模型。
- 数据库 schema 和迁移，除非任务明确要求。
- 生产依赖和真实凭证；真实凭证永远不得提交到 repo。

## 7. 工程责任边界

- 身份与权限：微信登录、手机号、后台账号、角色权限。
- 用户档案：问卷、协议、隐私确认。
- 活动供给：餐厅、活动批次、用户可见活动。
- 订单支付：订单、库存锁、测试支付、支付回调。
- 退款取消：用户取消、运营审核、自动退款、退款回调。
- 排桌履约：规则引擎、人工确认、成团/失败。
- 信息解锁：付款后、成团后、T-24 地址和导航。
- 评价风控：评价、举报、黑名单。
- 审计安全：高风险操作审计、日志脱敏、越权防护。
- 运行任务：锁单、排桌、解锁、通知、退款重试。
- 测试文档：自动化测试、手动 QA、README、AGENTS、发布说明。

## 8. 不可变更契约

未确认不得修改：

- 对外产品定位。
- 禁用词策略。
- 数据采集范围。
- 订单、支付、退款状态机。
- 活动、桌位、地址解锁规则。
- 用户和后台权限模型。
- 支付回调和退款回调幂等逻辑。
- 数据库 schema 或持久化格式。
- 公共 API 路径、参数和响应格式。
- 配置文件格式。
- 生产依赖。
- 部署拓扑。

M2.1 固化的状态机契约：

- 可报名活动状态仅为 `PUBLISHED` 或 `REGISTRATION_OPEN`；`DRAFT`、`CANCELED`、`COMPLETED` 等状态不得创建订单。
- 报名必须早于 `registrationEndsAt`，容量必须基于数据库订单真实计数。
- 容量占位口径：`PENDING_PAYMENT`、`PAID_PENDING_GROUP`、`GROUPED`、`REFUND_REVIEWING`、`REFUNDING`、`COMPLETED` 计入容量；`CANCELED`、`REFUNDED`、失败或关闭订单不计入容量。
- 支付成功回调只允许 `PENDING_PAYMENT -> PAID_PENDING_GROUP`；重复成功回调幂等；`CANCELED`、`REFUNDING`、`REFUNDED` 不得被改回已支付。
- 用户取消后进入运营审核，不能直接退款成功。
- 退款审批只允许审核中或失败重试的退款进入 `REFUNDING`；已 `REFUNDED` 后不得再次审批回退。
- 退款 callback 必须以 `refundId` 为主，且退款单与订单都处于 `REFUNDING` 后才能成功。
- 关键拒绝和状态变化必须写入 audit log。

M3.0 provider 契约：

- provider 只返回外部通道结果，不直接写订单状态。
- mock provider 必须保持现有 mock 登录、手机号、支付、退款路径兼容。
- real provider skeleton 缺少必需配置时拒绝启动或拒绝处理请求。
- real provider 不得 fallback 到 mock，不得 silent success。
- 真实微信支付/退款 callback 后续只能进入 API 状态机 helper，不得直接写 `Order.status`、`Payment.status` 或 `Refund.status`。

M3.1 身份 provider 契约：

- `AUTH_PROVIDER=wechat` 通过微信 `jscode2session` 换取 openid/unionid，`session_key` 不返回给业务层或小程序。
- `PHONE_PROVIDER=wechat` 通过 access_token 与手机号授权 code 换取手机号。
- 缺少 `WECHAT_MINIAPP_APP_ID` 或 `WECHAT_MINIAPP_APP_SECRET` 必须失败，不得 fallback 到 mock。
- provider 不直接写 `User`，用户创建和手机号更新仍由 API 层完成。
- 日志不得打印登录 code、手机号授权 code、session_key、AppSecret、access_token 或手机号明文。

M3.1.1 真实身份联调契约：

- 真实 AppID/AppSecret 只能通过 shell 环境变量、部署平台 secret 或仓库外本地 secret 文件注入，不得写入 repo。
- 推荐仓库外本地 secret 文件路径为 `/Users/marvin.x/.config/fanju/wechat-identity.env`，且建议设置为 `chmod 600`。
- 缺少 `WECHAT_MINIAPP_APP_ID` 或 `WECHAT_MINIAPP_APP_SECRET` 时必须明确失败，不得 fallback 到 mock。
- API 不得向前端返回 session_key。
- provider 失败不得创建脏用户，不得覆盖旧手机号。
- 联调前后必须保持状态机探针通过。

## 11. Subagent 和 Goal 使用建议

- 适合 subagent：Explorer、Test Worker、Documentation Worker、Reviewer。
- 谨慎使用 subagent：Data Worker、Integration Worker、Interaction Worker。
- 不适合交给 subagent 独立决策：技术栈、schema、订单/支付/退款状态机、权限模型、产品定位。
- Goal 使用建议：每个里程碑一个 goal，不要一个 goal 覆盖全部 MVP。

## 12. 暂停条件

Codex 遇到以下情况必须暂停问人：

- 技术栈未确认。
- 需要新增生产依赖。
- 需要真实微信支付、生产密钥或商户号。
- 需要采集身份证、性别、年龄、实时定位、通讯录或其他敏感数据。
- 需要改变退款规则。
- 需要改变产品定位或用户可见文案边界。
- 需要更改数据库 schema 且无迁移方案。
- 需要执行不可逆迁移或删除数据。
- PRD 与代码库现状冲突。
- 验收标准不可验证。
- 权限、安全或隐私风险无法消除。
- 多个任务会修改同一核心文件导致冲突。
- 测试无法运行且没有替代验证路径。
