## 当前代码依据

- `app.ts` 成团/失败事务提交后才调用 `enqueueInboxNotifications`；失败只记 warn。`Notification` 创建时直接标 `SENT`，但此时没有真实外发。重复成团幂等返回也不会补建遗漏通知。
- `Notification` 没有业务事件唯一键。`worker.ts` 的生产兼容入口只处理已可信资金事件；`local-recovery` 有明确 mock/本地环境门禁。通知任务类型、发送者、失败待办和导航尚不存在。
- `server.ts` 监听失败会断库退出，但没有 SIGTERM 停接新请求与排空；`/health` 固定 `{ok:true}`，不能证明数据库或 worker 就绪。A2 已有 30 秒租约和 8 次预算，但整体发布组合与真实备份恢复仍未签收。

## N1 切片

| 切片 | 事务与接口 | 验收 |
| --- | --- | --- |
| N1a 站内可靠落盘 | L2 成团事务为每个用户写入唯一 `(businessEventId,userId,type)` 通知；状态从 `PENDING` 起，关联订单/活动但 payload 不含地址或手机号；同事务写持久任务 | 事务失败无成团半提交；提交后杀 API 仍保留记录；重复确认每人一条 |
| N1b 投递和补偿 | 独立 worker 处理通知任务，租约代次防旧 worker 覆盖；失败按既有退避/预算，MANUAL 有责任人和截止时间；`SENT` 仅表示站内消息已可读取或真实渠道确证 | worker 崩溃/接管/重复执行不多发站内消息；第 8 次后进入待办；不能以 createMany 当已送达微信 |
| N1c 用户与运营入口 | 本人分页消息、关联本人订单，异常工单/通知失败只让相应运营角色看到；明确已读/未读与导航失效 | 跨用户拒绝；订单/活动状态变化后导航仍由服务端重新鉴权；运营能定位失败任务并记录处置 |

微信订阅消息另需模板、用户授权、密钥和真实渠道专项批准；站内消息验收不能代替这一步。

## P1 切片

| 切片 | 行为 | 验收 |
| --- | --- | --- |
| P1a 就绪与停机 | liveness 只看进程；readiness 检查数据库、必要迁移及必需 worker 消费能力；SIGTERM 先停接新请求，限制排空时间，断开连接 | 断库 readiness 失败；停机期间未确认的事件/任务由新进程接管；不丢 ACK 后可信事件 |
| P1b 运行诊断 | 请求/订单/支付/退款/任务关联 ID；错误分类、待办数、最旧任务延迟、账单覆盖状态与告警；敏感字段结构化脱敏 | 故障从订单 ID 可定位至任务和资金事实；日志样本无手机号、code、secret、完整渠道报文 |
| P1c 备份和恢复 | 保存迁移版本、产物摘要、部署配置校验；隔离恢复后按渠道账单反查本地，再处理存量任务；记录停止新收费与恢复准入 | 人为删除恢复快照中的 receipt/job 后仍能发现渠道有本地无；账单不可用显示覆盖不完整，不恢复新收费 |
| P1d 版本矩阵 | L1/L2 Schema 切换后的最低兼容 API/worker/ops/weapp 提交及摘要，实际升级/回退演练 | 不用 `bc25f5b` 假装兼容新历史订单；回退保留资金记录和新字段，无 delete/drop |

真实部署环境、备份介质、支付商户模式、账单来源、值守人和域名仍无现场证据。上述本地实现可在获准的隔离环境验证；生产部署、密钥注入、真实账单/微信请求、收费与公开发布仍按 G2–G4 独立批准。
