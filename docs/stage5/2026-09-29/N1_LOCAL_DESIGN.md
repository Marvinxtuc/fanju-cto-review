# N1/P1 本地恢复专项设计准入稿

2026-09-30。根据当前代码重新核查 `N1_P1_RECOVERY_TASKS.md`。本稿用于下一包本地实施评审，不代表生产部署、真实通知或备份恢复批准。

## 已有机制与实际缺口

L2 已在成团事务内写入 `Notification.businessKey` 唯一通知，并同事务写 `DELIVER_INBOX` 持久任务。失败成团和运营取消也复用该机制。`local-recovery` worker 会执行 `deliverInbox`，它把 `PENDING` 改为 `SENT`；这个 `SENT` 仅指站内消息可读取，没有微信外发。当前 `/api/notifications` 却会返回未投递的 `PENDING`，仅取前 50 条，也无已读、订单关联和稳定游标。生产允许的 `events-only` worker 不消费 `DELIVER_INBOX`，所以正式组合不能仅凭现有代码声称通知可用。旧任务单中“没有业务键、创建时直接 SENT”的描述已过时。

`/health` 只返回固定响应；`server.ts` 没有排空停机。资金任务已有数据库租约、代次、8 次预算和 `MANUAL` 待办，但缺少可观测的 worker 心跳。账单导入和本地对账模块已存在，恢复后的渠道反查演练、最低兼容版本与备份介质仍未完成。

## N1 本地实施契约

1. **通知状态**：保留 `PENDING → SENT` 站内投递语义。本人列表只返回 `SENT`；使用 `(createdAt,id)` 稳定游标，服务端限定页大小并返回 `nextCursor`。新增 `readAt`，只允许本人把已送达通知标记已读，重复请求幂等。通知关联不可变 `orderId`/`activityId`，列表只给导航标识；点击订单仍重新调用已有本人鉴权接口。迁移先加可空字段、回填已有业务键可解析的记录，再收紧新写入。旧通知不能自动猜测订单归属。
2. **worker 与失败**：增加 `inbox-only` 运行模式，只领取 `DELIVER_INBOX`，不加载真实资金渠道配置，也不执行支付、退款。复用已有 `runOne`、租约和重试；`deliverInbox` 在事务中用 `PENDING` 条件更新，因此旧 worker 恢复只会幂等读取，不会重复产生站内消息。超预算进 `MANUAL`，运营可按任务 ID 追到通知、用户与订单；任何重试都不写外发渠道。
3. **补偿**：提供只读审计/修复预览，找出 `PENDING` 无任务、`SENT` 但任务未收敛、业务键重复等差异。仅对有完整业务键、订单归属和允许状态的遗漏项补建任务；不重新发微信、不删除历史通知。成团重复确认、进程在提交后退出、租约过期双 worker 接管均纳入隔离数据库测试。
4. **运营与用户**：小程序通知列表按页加载并明确未读；失败通知仅运营角色可见，待办认领/复核沿用 O1 的具名机制。通知 payload 不含地址、手机号、openid 或渠道报文。

## P1 本地实施契约

1. **就绪与停机**：保留 `/health` 作为兼容 liveness；新增 `/ready` 检查数据库短超时、必要迁移标识，以及必需 worker 消费模式的心跳新鲜度。worker 心跳以数据库时钟写入独立表，含模式、实例、版本和最后成功轮询时间；读写接口不泄露环境变量。API 收到 SIGTERM 先停止新连接，最多等待现有请求的限定时间，再断开 Prisma；未完成任务保留租约供下一实例接管。真实回调只在可信事件落盘提交后应答。
2. **诊断**：按订单 ID 只读查询关联支付、退款、收款事实、退款义务、持久任务、异常待办。指标显示 READY/RETRY/RUNNING/MANUAL 数、最旧可执行任务延迟、账单覆盖状态。日志只保留内部 ID 和错误分类；手机号、code、密钥、原始通知与完整渠道流水不进入日志或诊断响应。
3. **恢复演练**：在新建可丢弃数据库执行全部迁移，保存本地快照和产物摘要；故意用缺少一笔本地收款记录/任务的测试快照恢复，再导入受控 mock 渠道账单，证明能发现渠道有、本地无。账单不可用或覆盖不完整时 readiness/运营面必须显示不能恢复新收费。先核对渠道，再跑恢复任务，最后逐笔关异常；不得以任务重放代替对账。
4. **版本矩阵**：列 Schema、API、worker、ops、weapp 的允许组合及 SHA/产物摘要，逐项演练升级与回退。退出旧订单唯一约束后的最低回退提交不能写 `bc25f5b`；必须在形成兼容提交并实际演练后填写。回退不得删除资金、通知或审计记录。
