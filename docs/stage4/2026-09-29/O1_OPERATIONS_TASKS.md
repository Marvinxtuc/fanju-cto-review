## 当前代码事实

- `App.tsx` 已有受控本地管理员登录、列表、排桌、退款通过、举报处理和部分活动履约按钮。`views/RestaurantsView.tsx`、`ActivitiesView.tsx`、`OrdersRefundsView.tsx` 仍是静态示例；不可拿它们证明真实管理流程。
- API 已有 `POST /api/ops/restaurants` 和 `POST /api/ops/activities`，但主界面没有创建表单；缺少餐厅编辑、活动草稿到发布/关闭/运营取消、退款审核拒绝及异常任务完整处置入口。
- 运营列表只取前 50 条，审计取前 100 条；这些是窗口，不是总数。`cors` 当前 `origin: true` 且未列 DELETE；生产跨源来源与超级管理员解除黑名单的预检组合尚未验证。
- 餐厅/活动创建没有审计；活动字段目前只做单字段范围检查，缺少 `registrationEndsAt <= startsAt < endsAt`、`minSize <= targetSize <= maxSize <= capacity`。举报处理读 OPEN 后更新，需并发一次性确认。

## 分包、依赖和证据

| 包 | 精确范围 | 验收 |
| --- | --- | --- |
| O1a 供给写入 | 餐厅创建/编辑，活动草稿/发布，服务端交叉校验、禁用词、角色和审计；前端表单显示校验/失败 | 空库登录后创建餐厅与活动，错误时间/人数/费用/角色明确拒绝；审计可追踪且无电话明文 |
| O1b 生命周期 | L2 运营取消、成团失败、确认/履约状态接口接入 UI；高风险动作明确原因并防重复 | 真实 PostgreSQL 走完发布到成团或失败；取消生成逐笔资金义务，不通过前端直接改状态 |
| O1c 退款与异常 | L2 拒绝审核、A2 金融待办只读/受控结案，状态、责任人、期限与原流水摘要 | 并发审批只有一次有效结果；已收款异常可从订单找到；结案要求不同复核人和证据，不手改资金 |
| O1d 列表与网络 | 服务端分页/聚合统计、前端游标，最小 CORS 来源/方法矩阵 | 51 条订单/活动不会从界面消失；容量按 L1 口径统计；跨源 DELETE 仅批准来源及角色可用 |
| O1e 反馈和审计 | 黑名单解除 UI、举报 CAS、餐厅/活动/退款操作审计、失败提示 | 重复举报处理只写一次；不同角色在 API 与 UI 均受约束；审计无敏感内容 |

每包先冻结兼容路由和管理员角色矩阵，按真实 PostgreSQL/HTTP 路径验证，再以真实 Vite 产物打开页面。共享写入逻辑由 L1/L2 的事务 helper 提供；O1 不复制状态机。运营需给出具体用户、活动和餐厅数据的可丢弃验收场景；真实商户资料与凭证只在单独授权环境使用。

## 阻塞与回退

O1b/O1c 依赖 L1/L2 通过设计及本地实现；O1a 的草稿/发布契约和餐厅编辑公开路由仍须明确权限与审批。跨源部署需要确定正式运营域名，未知时只验证本地同源/受控测试源。回退停新管理写入、保留已创建供给/审计/资金记录，不删数据；兼容 API/客户端提交 SHA 须实际产生后再填写。
